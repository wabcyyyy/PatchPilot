## 1. P0 严重：核心承诺可被绕过

### P0-1 「只采信测试」的判定地基，可被一次 `conftest.py` 改动整体造假

- **实证**：基线 `rc=1, failed=1`；仅改仓库根 `conftest.py` 加 `pytest_collection_modifyitems` 给失败用例打 skip 后 →
  `rc=0, skipped=1, all_passed=True`。
- **根因（两条独立且叠加）**
  1. `app/adapters/pytest_adapter.py:57` — `all_passed = exit_code == 0`，不看 `skipped`，也不校验"请求的 node id 是否真的跑了并通过"。
     `PytestReport.skipped`（`:48`）采集了但无人使用。
  2. `app/tools/paths.py:13-19` — `is_test_file` 只认 `tests/`、`test/` 目录与 `test_*.py`、`*_test.py` 命名。
     `conftest.py`、`pytest.ini`、`setup.cfg`、`tox.ini`、`pyproject.toml` 的 `[tool.pytest]` 段全部不算测试文件。
- **影响面（精确）**：`app/graph/nodes.py:331` 的 `resolved` 判据 = `verify_failed_ok and verify_regression_ok`，二者均为 `all_passed`；
  `app/evals/driver.py:180` 的 plain 引擎同理。28 道官方题目前**侥幸安全**——全部 manifest 写了 `allowed_paths: src/**`，把 `conftest.py` 挡在范围门禁之外；
  但 `app/api/schemas.py:20-22` 明确允许 `allowed_paths=None = 不设白名单`，**自定义仓库任务完全暴露**。命中 AGENTS.md 禁区第一条。
- **整改**：① `all_passed` 改为按期望 id 集合判定——从 junit XML 取实际 `testcase`，要求期望的每个 id 都存在且既非 failure/error 也非 skipped；
  ② `is_test_file` 增补 pytest 控制面文件名单。约十几行，须配套新增攻击样例。

### P0-2 「路径越界」门禁是死代码，实际拦截者是 `git apply`

- **实证**：`normalize_rel('../../../escaped.py')`→`'escaped.py'`；`'/etc/passwd'`→`'etc/passwd'`；`'.git/config'`→`'git/config'`。
  对应 diff 过 `run_gates` → **`ok=True`，零 violation**。
- **根因**：`app/tools/paths.py:23` 用了 `lstrip("./")`。`str.lstrip` 接受的是**字符集合**而非前缀，会把开头所有 `.` 与 `/` 连续剥光。
  于是 `app/graph/gates.py:83` 的 `".." in parts` 与 `rel.startswith(("/", "\\"))` 所依赖的字符在送达判断前已被吃掉——绝对路径分支**永不成立**。
- **是否可被利用：否。** 实证 `git apply --check` 对 `../` 穿越返回 `rc=128 / error: invalid path`；对 `/etc/x.txt` 因 `-p1` 剥离落在工作区内。
- **代价**：`docs/threat-model.md:41` 把"路径越界"列为第一道防线，`docs/design.md:21-23` 声称工具层与节点层两道——实际两道恒过，
  纵深防御塌成单层，且唯一那层是 git 的隐式行为而非本项目代码。
- **整改**：`normalize_rel` 改用 `PurePosixPath(rel).as_posix()` 或 `re.sub(r'^(\./)+', '', s)`；顺手修 `.git/`→`git/` 降级；补 3 条单测钉住（`../x`、`/x`、`./../x`）。

### P0-3 PM-001 的复盘修复装在一个生产永不调用的函数里

- **证据**：生产建工作区只有 `app/evals/driver.py:114` 与 `app/graph/nodes.py:65` 两处入口，均调 `app/gitops/testing.py:47 materialize_repo`。
  `app/gitops/snapshot.py:32 create_workspace` 全仓 **0 个生产调用方**（仅 `tests/` 与 `scripts/demo_gitops.py:33,45`）。
  而 `docs/postmortems/PM-001:18` 改进项①「两个方向的包含关系都要拒绝」正是实现在 `snapshot.py:41-44`。
- **实证对比**：同一"目标嵌套于源仓库内"输入，`create_workspace` 干净抛 `TaskError`；`materialize_repo` 直接进 `copytree` 递归展开，
  报出 `...\workspace\runs\task1\workspace\...` 的 `shutil.Error`。
- **二次伤害**：`tests/test_gitops.py:47 test_create_workspace_refuses_to_shadow_source` 是绿的 → PM-001 在测试视角"已修复且有回归覆盖"，
  实际覆盖的是死代码。
- **整改**：把 containment 与 `is_git_repo` 校验移入 `materialize_repo`，随后合并 `snapshot.py`/`testing.py` 为单一实现；勿再留两份。
