1. 当前项目 #

PatchPilot 是 Python/pytest 仓库的测试失败诊断与补丁验证原型，服务面是 FastAPI，

任务与轨迹落 SQLite，Redis 可选地承担任务锁。CLI submit 是 HTTP 客户端。

模型层为 OpenAI 兼容客户端或离线 FakeLLM；不做向量检索、跨任务长期记忆或官方 SWE-bench 评测。

测试数量不作为固定能力，历史发布收据只证明当时提交/dirty/环境下的结果。

2. 完整执行链 #

  1. TaskCreateIn/路由 → TaskService 校验仓库与模型开关，构建完整 TaskSpec 哈希幂等键。
  2. custom 输入复制冻结并核对指纹，预检环境；Docker 预检只查 daemon，真实收集由容器基线确认。
  3. 契约写文件与 SQLite，再进入线程池；执行先交叉复核受理身份。
  4. graph runner 从受理策略重建任务配置、模型 runtime 与账本，物化独立 Git 工作区。
  5. baseline 验证失败集真红、回归真绿；localize 用 AST 骨架、符号与字面检索读证据。
  6. issue-only 路径由 diagnose 提出具体测试，平台重做红/绿基线，经 trusted_user 批准后冻结清单。
  7. plan 产生文本计划，propose 运行工具循环；块锚定补丁经编译、门禁、git apply 与语法/落点复检。
  8. apply 冻结候选；verify 平台独立跑失败/回归集，按 JUnit 完整身份匹配，开启时再双跑比对。
  9. finish 使用共享 acceptance，graph 另校验候选绑定。失败经 rollback 留证、复位、回 plan。
  10. JSONL/SQLite 保存轨迹，report.json 记录引擎证据，tasks 保存服务生命周期。取消/迟到事件不能复活终态。

3. graph / plain 与 LangGraph #

graph 明确阶段拓扑、条件边与 superstep 检查点。模型在阶段内自主选工具，不能任意改变平台阶段或 verdict。

真正模型工具循环在 run_plain_loop，graph、plain 与子任务都调用。

plain driver 是单轮基线/循环/平台验证，不具有 graph 的诊断审批、多轮候选或自动恢复编排。

两者共享工具、pytest adapter、final_acceptance；共享判定不等于功能等价。

LangGraph 本身不保证恢复正确：平台还必须重建 ctx、读候选与账本、清旧结论并重验。

01 · 项目介绍 #

一句话 #

PatchPilot 面向 Python/pytest 仓库做测试失败诊断与补丁验证，平台独立执行测试并计算验收结论。

30 秒 #

“你提交仓库和缺陷描述，Agent 检索、提出补丁，平台在独立工作区验证原失败集与回归集。

resolved 要求补丁非空、双集全通过、门禁通过、预算内且未取消。它是可运行原型，

离线回放验证控制链；历史真实 SWE 实验有限，不宣称生产可用或官方成绩。”

90 秒 #

“LangGraph 负责阶段拓扑和检查点，每个模型阶段内部复用手写工具循环。

工具 schema 与执行能力来自同一阶段集合；AST/符号/字面搜索辅助定位，原始证据可分页取回，

平台观测进入任务记忆，模型只能写引用假设。块补丁经门禁和 Git/语法复检后，

平台重新跑具体测试，使用完整 JUnit 身份而非只看返回码。

最终共享 acceptance 不采信 finish 声明；graph 还绑定冻结候选，恢复时重应用并重验。

默认 local 不是沙箱，容器后端与单进程服务也有部署边界。

FakeLLM 回放含答案；真实模型与消融有历史记录、样本偏差和负结果，不能作为当前版本泛化收益。”

3 分钟补充 #

受理 TaskSpec 完整 hash 幂等、冻结 custom 输入副本、预检后双写契约，提交线程池。

Docker 预检不在宿主导入目标 conftest，只查 daemon；真实收集由容器 baseline 确认。

执行按受理配置建模型、账本与 runtime；未知消耗继续占预算，恢复不重授。

issue-only 清单由模型提议、平台基线复核、trusted_user 批准，不让模型自定成功标准。

失败回滚保全证据再复位、至多消耗一次轮次；任务终态与 stage 分开，迟到事件不能复活取消任务。

plain 是单轮替代驱动，共享工具循环与验收，功能不等同 graph。

证据与边界 #

详细链路见 事实基座，实验见 评测口径。

开发只跑 verify.ps1 定向检查，完整回归交 CI；历史收据不代表当前提交通过。

不要用源码行数、commit 数或测试总数推断 AI 参与比例、生产能力或修复率。

02 · 当前架构与取舍 #

M1 · API 与任务受理 #

FastAPI 同步路由校验输入，TaskService 构造 TaskSpec 完整哈希作幂等键；在途同契约返回原任务。

custom 输入冻结后预检，契约双写到文件/SQLite，再交线程池。CLI submit 通过 HTTP 调服务。

API 按单进程原型设计，默认鉴权/仓库白名单未启用，多租户与负载能力未证明。

代码：api/routes.py、service.py、preflight.py、schemas.py；测试：test_custom_task、test_preflight。

M2 · graph 与 LangGraph #

builder 定阶段/条件边，节点闭包持有工具上下文，可序列化 TaskState 进 checkpoint。

repair：prepare/baseline/localize/plan/propose/apply/verify/finish；issue-only 多 diagnose；失败经 rollback 重规划。

图提供明确阶段边界与恢复位置，平台仍要实现工具循环、预算、候选重应用与重验。

选择代价是闭包重建与阶段状态维护；不能声称框架自动保证恢复正确。

代码：graph/builder.py、nodes.py、runner.py；测试：test_graph、test_plan_invariants。

M3 · 共享工具循环与 plain #

run_plain_loop 发请求、结算 usage、执行阶段工具、维护消息/快照、处理文本完成协议与取消。

graph 的模型阶段和子任务都复用它。plain driver 单轮运行此循环，另行编排基线和平台验证。

两引擎共享 tools/pytest adapter/acceptance，但 graph 的审批、候选恢复与多轮编排不属于 plain。

代码：graph/plain_loop.py、evals/driver.py；测试：test_plain_loop、test_driver、test_frozen_policy。

M4 · 工具与能力边界 #

registry 同源产生 schema 与执行入口，阶段白名单限制可见与可执行集合；finish 为完成协议工具。

候选补丁写入口 apply_patch，另有 scratch、假设记忆与问答持久写入。run_tests 只选平台预定义集合。

reset_workspace 在 plain 全量工具表可达，graph 阶段未开放；不因一个入口无调用就删公开工具。

恢复策略区分 safe_replay/state_check/no_rerun；未知工具保守不重跑。

代码：tools/registry.py、base.py、paths.py；测试：test_tool_capabilities、test_tool_recovery。

M5 · 模型与配置 #

OpenAI 兼容 SDK 薄封装，无模型响应流式；SDK/平台重试互斥，协议错误携带计量事实。

能力显式声明与来源，不按模型名猜窗口；served_model 是观测，不证明别名背后的服务版本。

TaskRuntime 冻结窗口/输出能力；settings_for_policy 给每任务配置副本，保留受理预算/后端/超时/模型名。

旧契约缺字段走兼容回退，外部价格文件与服务端版本不能仅靠 profile 名保证不变。

代码：llm/openai_client.py、usage.py、profiles.py、agent/runtime.py、task_spec.py；测试：test_llm、test_frozen_policy。

M6 · localization / evidence / memory / 仓库规则 #

AST 骨架 + rg 文件预筛 + Python 字面逐行匹配 + 符号跳转，不是向量 RAG，无召回质量成绩。

工具回执先结构化裁剪再序列化，原文落 evidence，read_evidence 按工件游标分页。

TaskMemory 分平台观测与引用假设，修改后引用可 stale；ContextAssembler 按阶段/轮次幂等装配。

仓库说明从输入副本加载，目录说明按观测激活；规则进入上下文但不进入权限判定。

没有跨任务长期记忆。容量不够且保护区压不动时停止，不把软阈值当任务累计预算。

代码：context/、tools/search.py、symbols.py、memory.py；测试：test_evidence_store、test_task_memory、test_repo_instructions。

M7 · 执行器与 Docker #

local_runner 用 argv/Popen、环境白名单、超时进程树清理；默认 local 共享宿主权限，目录副本不是沙箱。

pytest Docker：--rm、网络、内存/CPU、workspace/reports 挂载与 uid 对齐。

诊断 run_command Docker 另带 PID 限额、no-new-privileges；不能把其参数套到 pytest 路径。

受控 profile 不接受自由 shell；write_repro 写 scratch，命令在诊断副本运行。

Docker custom 预检只查 daemon，不宿主 collect；容器内依赖/收集由 baseline 确认。

默认执行器镜像依赖有限，题目 env 可使用自带镜像；compose socket 是部署边界。

代码：executor/、tools/commands.py；测试：test_backend、test_command_profiles、test_docker。

M8 · Git 与补丁 #

冻结输入与物化工作区为物理副本、重建 Git 基线，不是 git worktree。

模型块锚定协议编译 unified diff，经门禁、git apply --check、落点检查、apply、TOCTOU 与 Python 语法复检。

回滚先保全 diff 再 reset/clean 并验证干净。不能删用户原仓库或把失败现场伪装为空补丁成功。

代码：gitops/、tools/patching.py；测试：test_gitops、test_blockpatch、test_attacks。

M9 · pytest 身份 #

JUnit file/class chain/name/参数化身份对应具体 node ID；缺失、歧义、跳过不能算通过。

退出码为零不够，平台必须重新验证声明的双集。签名规则保持现有归一化，不因文档校准改变。

重复运行一致只能检测部分 flaky，不能防住预置伪绿或证明补丁语义等价。

代码：adapters/pytest_adapter.py、test_identity.py；测试：test_test_identity、test_backend。

M10 · 门禁与终局 #

五类静态补丁检查在 run_gates，命令与资源门禁各在执行路径；不是七个互相独立的最终布尔字段。

共享 final_acceptance 要求验证通过、gate passed、非空diff、within_budget、未取消。

graph 还比当前 diff/候选 hash、冻结 manifest 与本次 verification_attempt_id。plain 无该恢复链。

规则可审计但不能防住指定测试上的过拟合；不让模型 judge 代替平台判断。

代码：graph/gates.py、acceptance.py、candidate.py；测试：test_acceptance、test_candidate_checkpoints。

M11 · 持久化 / 幂等 / 恢复 / 资源 #

tasks/trajectory_events/patches 为当前三张业务表，去重迁移另保存 duplicates 归档。

SQLite WAL 与连接线程锁；终态原子写，stage 独立进度；Redis 可选任务锁，未证明多实例领取安全。

checkpoint + loop/session/memory + candidate + ledger 决定四态恢复；写阶段重验，END只核对读报告。

账本预留/结算/未知持有，不重授；损坏账本标unknown且阻止新请求，不能当成全新额度。

费用为micro-USD估计，非真实账单；恢复deadline保留停机时间，用户等待顺延受绝对寿命封顶。

代码：storage/、graph/resume.py、resources.py；测试：test_candidate_recovery、test_budget_reservations。

M12 · 用户交互与子任务 #

graph 问题/回答/纠偏落盘，回答与批准是可信用户事件，不能修改冻结测试/金额/权限边界。

headless 需要澄清或批准时如实待审，不能自动伪造同意。会话修补孤儿 tool_calls 只给明确占位回执。

三种冻结角色，单层有限委派、独立会话与父预算切分，默认关闭；子结论不能覆盖父验收。

角色模型工厂由service/CLI注入，缺独立Fake脚本不能偷偷沿用父游标或发付费调用。

代码：agent/control.py、session.py、subtasks.py；测试：test_waiting_input、test_subagent_wiring。

M13 · 评测 #

自建题、版本化指标、manifest批定义、控制身份与观测分离；one_shot是评测CLI臂，API拒绝。

SWE适配器复用平台pytest与验收，可用官方镜像，但不是官方harness/成绩。

04 · 最重要的 20% 代码精读 #

选段标准：面试会问的机制，恰好落在这几段里。每段结构：代码 → 它在干什么 → 为什么这么写 → 会被怎么问 → 顺手讲的 Python 语法点。 行号以当前 HEAD 为准，可当场打开核对。

1. 请求入口：受理只做"决定要不要做"，不做"怎么做" #

# app/api/service.py（节选逻辑）
spec = build_task_spec(..., max_turns=DEFAULT_MAX_TURNS, ...)
idem_key = spec.task_spec_hash           # 任务身份 = 契约哈希
existing = repo.find_by_idem_key(idem_key)
if existing: return existing_row, False  # 幂等：同 spec 第二次进来不再开新任务
lock = build_lock(settings.redis_url)    # 默认 InMemoryLock
lock.acquire(f"task:{idem_key}", ttl=settings.task_timeout_seconds + 60)

在干什么：把"这次请求要不要执行"变成一个纯哈希比较 + 一把带 TTL 的锁。

为什么：客户端重试（网络抖动、用户多点一次）在无幂等的设计里就是双份钱 + 双份工作区。

会被怎么问："幂等键为什么用 spec 哈希而不是 request id？"→ 因为语义是"同样的输入就是同一个任务"，与客户端身份无关；代价是 DEFAULT_MAX_TURNS=20 竟然参与身份（service.py 硬编码、不是 Settings 项），改它会让历史任务的哈希漂移——这是我愿意承认的设计瑕疵。

Python 语法点：@lru_cache + 冻结 dataclass。get_settings() 带 @lru_cache（config.py）意味着 Settings 在进程内是单例，测试必须显式清缓存——conftest.py 的 _fresh_settings 就是 autouse 夹具在每条用例前后清一次，因为它曾经造成过跨用例泄漏。这是"装饰器改变函数语义 → 测试必须配合"的典型样本。

2. Agent 内循环：五道检查的顺序就是设计 #

# app/graph/plain_loop.py（节选）
for turn_no in range(start_turn, max_turns + 1):
    if cancel_event is not None and cancel_event.is_set():
        raise TaskCancelled(f"cancelled at turn {turn_no} boundary")
    if deadline_epoch is not None and time.time() > deadline_epoch:
        raise _budget_error("task exceeded time budget ...", tokens_spent, ...)
    parked = _interaction_gate(turn_no)  # 等用户回答/纠偏
    if parked is not None:
        return parked
    messages, repaired = SessionState.repair_orphans(messages, recovery_policy)
# app/graph/plain_loop.py（节选，资源账本）
call_id = ledger.begin_call(stage=state_label, round_no=round_no)
ledger.reserve(
    call_id=call_id,
    stage=state_label,
    round_no=round_no,
    request_tokens=estimate_request(messages, schemas).total_tokens,
)

在干什么：每回合开头按固定顺序过 取消 → 墙钟 → 交互 → 孤儿配对 → 保护区容量 → 压缩 → 阶段份额 → 任务账本，然后才发请求。

为什么这个顺序：

  • 取消和截止是"必须立刻停"的，放最前；
  • 交互门放在配对之前，因为恢复后要"从同一处重新进入，恰好一次"（代码注释明写）；
  • repair_orphans 放在唯一发送点之前——注释解释了原因：严格端点遇到"assistant 声明了 tool_call 但没有回执"会直接 400，整题崩成 NEEDS_REVIEW；如果指望四个回填分支各自记得配对，就一定会有分支漏掉。
  • ledger.reserve 的注释是最值钱的一句："检查与登记在同一临界区完成，比较基数是已用 + 全部在途预留 + 本次预留。此前只看已用，两个并发请求各自都装得下就都发出去了，现金/额度上限形同一半。"→ 这是 TOCTOU 在预算上的版本，也是"我先只查再扣"的竞态修复。

会被怎么问："两个并发请求同时通过预算检查怎么办？"→ 指着这段说"我踩过，现在是原子预留 + 在途计入"。

Python 语法点：异常携带业务数据。BudgetError 带 tokens_spent/turns/last_content（errors.py），ModelTransportError 带 usage 信封——因为"钱已经花了"这个事实不能因为抛异常就丢账。这是 Python 里用异常做结构化返回而非纯控制流的正确姿势（也解释了为什么补丁应用失败不是异常而是 PatchApplyResult）。

3. 工具统一入口：可见即可执行，异常一律收敛 #

# app/tools/registry.py（节选）
spec = REGISTRY.get(name)
if spec is None:
    result = ToolResult.fail(f"unknown tool: {name}")
else:
    ctx.tracker.record(tool="tool_started", ...)          # 执行之前先广播
    try:
        bound = inspect.signature(spec.handler).bind(ctx, **args)   # ← 关键
        result = spec.handler(*bound.args, **bound.kwargs)
    except TypeError as exc:
        result = ToolResult.fail(f"bad arguments for {name}: {exc}")
    except Exception as exc:
        result = ToolResult.fail(f"{type(exc).__name__}: {exc}")

在干什么：用 inspect.signature(...).bind() 做参数校验；只有"绑定失败"才叫 bad arguments；其他异常统一变成 ToolResult 回填给模型；工具名前必须发一条 tool_started。

为什么这么写（注释里就是整改记录）："此前 except TypeError 会把 handler 函数体内的业务 TypeError 也误报成参数错误"——异常类型复用导致的误诊，这是 AI 生成代码里极其常见的缺陷，能讲出来就是审阅能力的证据。

tool_started 的价值："SSE 的 tool_started 与轨迹共享同一条事实（没有第二条进度来源）；崩溃在 handler 中途时，事件流上'已开始、无结果'与孤儿 tool_call 的恢复语义对得上。"→ 一条事实只有一个来源，这是可观测性设计而不是加日志。

会被怎么问："工具抛异常会整个任务挂掉吗？"→ "不会，工具异常收敛成一次失败的回执喂回模型，由它决定重试还是换路；但只有工具层的异常收敛，执行器/门禁的异常是分层上抛的。"

Python 语法点：

  • * 强制关键字参数：def execute(ctx, name, args, *, round_no=0, state="-") —— 防止位置参数误传；
  • @property 把判定规则藏在字段名下：all_passed 看起来像布尔，实际是一整套反伪绿算法（见 §6）；
  • 上下文管理器 + 锁：repository.py 用一把 threading.Lock 包住所有 SQLite 访问，配合 check_same_thread=False——这是"我自己管理并发正确性"而不是靠框架。

4. 候选补丁写入口：块协议 → 计算行号 → 双门禁 → 原子应用 #

# app/tools/patching.py（骨架，按调用顺序）
report = run_gates(skeleton_diff, allowed_paths=..., max_files=...)  # 门禁①：编译前形状
diff_text = compile_block_patch(patch_text)  # 锚点匹配 + 行号由平台算
report = run_gates(diff_text, ...)  # 门禁②：编译后产物
apply_result = apply_diff(workspace, diff_text)  # 不是异常，是结构体
# app/gitops/patcher.py（顺序）
landing = check_landing(paths)  # symlink → symlink_escape；resolve 逃逸 → path_escape
rc = git(["apply", "--check", "--whitespace=nowarn"], input_bytes=diff_text)  # stdin，不进 argv
snapshot = read_bytes_of_touched_py_files()
rc = git(["apply"], input_bytes=diff_text)
rescan = detect_escape_after_apply()  # TOCTOU 复扫
if rescan:
    git(["apply", "-R"], input_bytes=diff_text)  # 反打回
if not ast_parses(new_content):
    restore(snapshot)  # 语法失败按字节还原

在干什么：模型的补丁不是 diff，是块协议（*** Begin/End Patch + 锚点文本）。行号由 SequenceMatcher.get_grouped_opcodes(3) 计算（blockpatch.py），锚点 0 命中 / 多命中 / 乱序都直接拒。门禁跑两次是为了同时拦住"坏意图"和"坏编译产物"。

为什么：模型写 unified diff 最常见的失败就是行号偏移和上下文不符；把行号从契约里拿掉，失败模式从"打不上"变成"锚点不明确"，后者可以喂回模型让它自己修正。

会被怎么问："补丁部分应用了怎么办？"→ "git apply 全成或全不成，失败返回结构体；真正危险的是 TOCTOU，所以应用后再复扫一次，违规就 git apply -R 反向打回，反打失败也如实上报、不自动掩盖。"

Python 语法点：difflib.SequenceMatcher（标准库做行号计算，不用第三方）；bytes 快照 + os.replace 原子写（candidate.py 拒绝空补丁、tmp+replace 落盘）。

分级是未来生产化优先级，不代表当前仓库审查确认了同级缺陷。 铁律：禁止把生产化扩展说成已实现。本文每一节先给"当前真实情况（含代码位置）"，再给"缺什么 / 怎么补"。 讲法模板：「这条我已经有什么 → 这条我明确没有 → 上线第一步是哪个」。

P0（不做就不能对外提供服务） #

P0-1 Authentication / Authorization（鉴权与授权） #

维度当前真实情况（代码事实）缺口
AuthNapp/api/auth.py：Bearer token，secrets.compare_digest 定长比较；但 PATCHPILOT_API_TOKEN 默认空 = 完全关闭，只在启动时打一条 warning（app.py）；/api/health 永久豁免无用户体系、无 API Key 生命周期（签发/轮换/吊销）、无 session、无 OIDC
AuthZ无角色概念。任何能调 API 的主体可以对任意 bug_id / 任意 repo_path 建任务无资源级授权：谁能看哪个任务、谁的报告、谁的任务
输入约束PATCHPILOT_ALLOWED_REPO_ROOTS 默认空 = 不限制（config.py），且只作用于 repo_path 分支（service.py）；bug_id 走 pattern + bugs_root 校验（schemas.py、service.py）compose 里也传空（docker-compose.yml）

为什么是 P0：代码事实 的组合是"默认无鉴权 + 可指定任意宿主目录 + 该目录的 conftest.py 会被执行" → 若服务执行攻击者可控制的仓库，暴露默认无鉴权入口可能导致宿主代码执行。docs/threat-model.md 自己就是这么写的。

怎么补（顺序即优先级）：① 默认开启 token 并在非回环绑定 fail-fast（现在是 warning）；② ALLOWED_REPO_ROOTS 默认非空；③ 引入 principal 概念 + 任务归属行（tasks.owner），所有 GET/cancel/answer 校验归属；④ 令牌哈希存库（现在配置里是明文）；⑤ 走 OIDC/服务账号；⑥ 速率与配额绑定 principal。

面试口径："默认姿态是回环单用户，这是我明确不防的一项，写在威胁模型里。要对外服务，第一件事不是加权限模型，是把默认值从'不限'改成'拒'。"

P0-2 Rate Limit / 成本控制（最直接的烧钱风险） #

当前真实情况：没有任何限流（无中间件、无 429）。唯一的钱闸门是单任务预算：token_budget=200000、cost_budget_micro_usd=0（0=不限）、max_model_calls=0、llm_max_tokens=4096、default_max_rounds=5、max_turns=20，由 ResourceLedger 原子预留执行（plain_loop.py）。

缺口：全局并发只有 task_max_workers=2 这一个隐式限流；没有 per-user/per-IP 速率、没有每日配额、没有排队上限、没有"提交即扣额度"；budget_mode=tokens 默认按 token 而非钱，cost 只在有价目时才算得出（未收录模型 n/a）。

怎么补：令牌桶 per-principal + 队列上限 + 429/Retry-After；预算以"钱"为主单位并在受理时预扣（现在是执行中拦）；接入账单源做对账（pricing.py:provenance 明写"本仓库没有任何账单来源"，settled_bill 永远拿不到真值）；成本异常检测（单任务超 p95 阈值即熔断）。

P0-3 Sandbox（执行隔离成为默认路径） #

见 02 M7 与 03 的默认隔离风险。代码事实：docker 后端真实存在（command_runner.py：--rm --network none --memory 1g --cpus 1.0 --pids-limit 128 --security-opt no-new-privileges），但 execution_backend=local 是默认（config.py），执行默认 local，可显式选择 Docker，默认 executor 镜像依赖有限；题目 env 可自带官方或定制镜像，compose 挂 docker.sock，docker_only 无人使用。

怎么补：默认 docker；镜像按目标仓库 lock 文件构建（或让受理阶段要求提供镜像）；--read-only + tmpfs scratch；去 socket；每任务独立网络命名空间；用 gVisor/Kata 补内核面；宿主 env 白名单再删可写路径（现在仍透 TEMP/APPDATA/USERPROFILE）；资源配额加到 local 兜底路径上。

P0-4 可观测性：Logging / Tracing / Metrics #

  • Logging（有，代码事实）：stdlib logging，业务日志带 task_id（registry.py 的整改注释就是补 task_id 的现场）+ request_id contextvar（app.py）。
  • Tracing（无）：没有 OpenTelemetry，没有 span 父子关系；一次任务的因果链靠 trajectory.jsonl + SQLite trajectory_events（自增 id 作游标）。这已经比多数 Demo 强，但跨服务不可串联。
  • Metrics（无）：没有 /metrics，没有 Prometheus，没有 p95 延迟。app/evals/metrics.py 是评测指标不是运维指标，别混称。
  • 怎么补：OTel（trace + 模型调用 span，属性含 model/tokens/cost/latency/tool）；Prometheus 指标（任务终态分布、每阶段耗时、工具失败率、预算耗尽率、恢复次数、SSE 在线数）；结构化 JSON 日志 + 集中采集；把 trajectory_events 的自增 id 作为 trace correlation key。
  • 追问预案

    "你怎么发现线上任务变慢？"→ "我现在发现不了，因为没指标。我能做的是每次任务的 duration_ms 已经逐工具记录在轨迹里（registry.py），生产化只要把它聚合出来。"

P1（上线后一周内会出事） #

P1-1 Timeout / Retry / Idempotency（这三件事的真实状态） #

项有没有 / 弱点
Timeout请求级 llm_timeout_seconds=120；执行级 command_timeout_seconds=120 + 杀进程树；任务级 task_timeout_seconds=900 + 绝对寿命 86400s；受理级 intake_timeout_seconds=120没有 per-test timeout（只有整轮 pytest）；recycle_grace_seconds 与 acceptance_wait_seconds=3600 语义重叠；_execute 在 shutdown 时不 join 线程（service.py）
Retry传输层 allowlist + SDK/平台重试互斥（openai_client.py）；工具恢复策略 no_rerun/state_check（registry.py）没有语义级退避重试（429/529 都归传输处理）；崩溃恢复时"崩溃前落地的写"仍靠模型读恢复提示自行判断（session.py）；重试不重算预算（service.py）
Idempotency强：spec 哈希 + 锁 + 唯一索引 + 终态先到先赢（service.py、repository.py）锁 key 只在配 Redis 时才是跨进程的；InMemoryLock release 无持有者校验（docstring 自认，靠 DB 兜）

怎么补：给 pytest 加单测超时（pytest-timeout 不可信，因为不能要求靶仓装插件 → 由执行器按输出静默时长判停）；重试用满 exponential backoff + jitter 并区分 429/5xx；恢复时把"写类工具"的执行事实落到 ledger（现在只到轨迹）。

P1-2 Queue（任务队列） #

当前真实情况：没有队列。ThreadPoolExecutor(max_workers=2) + 立即受理，意味着提交 1000 个任务就创建 1000 个工作区目录和 1000 行 DB 记录，线程池自己排队，但磁盘和 DB 没人管（recycle_finished_workspace=True 只回收终态且超 grace 的）。

怎么补：外部 broker + worker pool（arq/Celery/Temporal）+ 队列深度上限 + 优先级 + 公平调度 per-principal；受理时入队而非起线程；加背压（429）。

P1-3 Cache #

当前真实情况：全系统没有任何缓存（Redis 只做锁）。已有的只是"同一进程内的重复计算复用"：上下文装配按 (stage, round_no) 幂等缓存并记 context_assembly_reused 事件（nodes.py）、get_settings() 的 lru_cache。

缺口 & 机会：模型层无缓存（同一 prompt 重复请求照样付钱）；无检索缓存。生产化的第一份缓存应该是响应级（prompt hash → completion，带 TTL 与 provider 计费口径），第二份是检索/仓库骨架（按 commit hash 失效）。

追问预案："为什么不用 Redis 缓存？"→ "因为我确实没用上。如果加，我会先用它缓存装配好的上下文骨架（键=仓库 commit+profile），因为那是纯计算且随任务重复；模型响应缓存要谨慎，因为它会污染非确定性回归。"

P1-4 Secret Management #

当前真实情况：.env + pydantic-settings；API token 与 LLM key 都是进程环境变量，明文在配置文件里。已有缓解：子进程 env 白名单重建（local_runner.py，注释点名 API_TOKEN/LLM_API_KEY 曾被不受信 conftest 读到，这是真实修复）；轨迹/快照按 key 名脱敏（tracker.py、provenance.py）；仓库说明里形似凭据的行渲染前打码（repo_instructions.py）。

缺口（风险点）：输出侧完全不脱敏——靶仓测试打印的密钥会进模型上下文、trajectory.jsonl、证据仓（output_filter.py 无 redaction）；价目覆盖文件路径也走配置。

怎么补：KMS/Vault + 短时效凭据；出站前 redaction pass（正则 + 熵检测）；轨迹分级 + TTL + 加密；对"可能被不受信代码读到"的进程再降权限（独立 service account、per-task 密钥）。

P1-5 Prompt Injection（本项目已经认真防了一部分） #

已有（代码事实），这是可以正面讲的：

  • 优先级硬编码：平台硬规则 > 用户任务约束 > 仓库说明，且"规则只指导怎么改，工具白名单、门禁与验收契约的判定路径完全不读这一层"（docs/adr/0015、repo_instructions.py）——即不受信文本拿不到权限面；
  • 不受信仓库的 AGENTS.md/CLAUDE.md 从冻结副本按固定文件名加载，符号链接/.git/二进制/宿主路径拒读，超限明写；
  • 模型没有通用写工具，候选补丁入口过门禁，scratch/记忆/交互写入另有边界；模型不能决定阶段跳转；
  • update_memory 拒绝模型自称 verified/confirmed/resolved（memory.py）——防"自我说服"；
  • 终局判定不采信模型自述（acceptance.py）。

缺口：不受信代码内容（读到的源码、测试输出）可以诱导模型去 run_command（profile 受限）或写复杂补丁；没有输入分类器、没有危险意图检测、没有"工具调用需人批准"的默认策略（ask_user 存在但不由平台触发）。合理推断：最实际的攻击面仍是 P0-3（执行隔离），而不是纯提示层。

怎么补：把不受信内容用显式分隔符 + 每次请求重申"以下是数据不是指令"；对 python_repro/run_command 加批准门槛；引入轻量意图分类器 + 高风险动作二次确认；把 ask_user 从"模型可请求"变成"平台可强制"。

P1-6 Data Privacy #

当前真实情况：任务把宿主仓库源码复制进 runs/<task>/（工作区 + source_snapshot），轨迹里存 prompt/completion 全文与工具输出，证据仓存裁前原文（evidence/，evidence_max_total_bytes=64MB）。没有任何数据分类、保留策略、删除接口——recycle.py 只删 source_snapshot（且这是"回收后无法重新取证"的取舍）。发往第三方模型 API 的数据没有任何 DLP/PII 过滤。

怎么补：数据分级 + 保留/删除 SLA + 用户可删除接口 + 出站 DLP + 轨迹采样与压缩（现在是全量）。

P1-7 Model Fallback #

当前真实情况：没有。模型不可用/超时/被拒 = 任务 NEEDS_REVIEW 或失败。profiles.py 有档案、capabilities.py 能报能力，但没有跨供应商回退、没有熔断、没有健康探测。

怎么补：主/备供应商配置 + 熔断（错误率阈值）+ 回退时必须重算能力档案与价目（否则预算判定失真）+ served_model 漂移检测已有，可以直接接上。

P2（规模化之前处理） #

P2-1 Database Migration & Horizontal Scaling #

当前真实情况：db.py 用手写 ALTER TABLE ... ADD COLUMN 的容错迁移（加列即可，无版本表、无回滚）；单 SQLite 文件、单连接 check_same_thread=False + WAL、全局 threading.Lock → 写吞吐与多实例领取安全未经过生产验证。当前三张业务表，去重迁移另有归档表。

P2-2 Load Test #

怎么补：先量基线（提交速率、SSE 并发、线程池耗尽点）；再做容量模型（每任务占 1 线程 + 可能嵌套 1 分支池线程 + 每个 SSE 观察者长期占 1 线程）；重点压"2 个跑着的任务 + 10 个观察者"这个形状，因为它现在就会把 ~40 线程的 anyio limiter 压住。

面试口径："没有压测数据，所以我不给任何 QPS 或延迟承诺——我能给出的是瓶颈在哪一段。"

P2-3 Failure Recovery（这条其实很强，讲的时候别把它降级） #

已有（代码事实）：LangGraph SQLite checkpoint（B 层）+ loop_state.json 回合边界快照（A 层，只在一致切点写、2MiB 上限、永不抛错）+ ledger_state.json + 冻结候选；prepare_resume 返回 continue/revalidate/already_terminal/reject 结构化决策；可写阶段强制重验证且清空 verify/gate 布尔；already_terminal 只重放工件不重跑；孤儿 tool_calls 用显式标注的占位回执修复并附恢复策略；真实进程崩溃有测试（test_resume_crash.py 用 os._exit）；demo/run_restart_resume_ticket.py 是可演场景。

缺：checkpointer 依赖缺失时静默返回 None（任务能跑但不可恢复，应 fail-fast，checkpoint.py）；没有跨机恢复（文件工件在本地盘）；没有"多久没心跳判死"的租约机制（只有锁 TTL）。

P0（26 条） #

A. 模型调用基础 #

1. Token 与 Context Window

token 是计费与容量的单位，不是字数；context_window 是输入+输出的总容量，很多失败源于只算输入。

本项目落点（代码事实）：四个概念各有名字和读数——单请求硬容量、软压缩目标、任务累计额度、单次输出上限（docs/adr/0014）；token_estimate_factor=1.0 只做本地估算与 provider 真值的换算；估算不出就记 unknown 且 unknown 一票否决 resolved。

面试口径：不要说"我的模型窗口是 128k"，要说"我不从模型名推断窗口，能力必须带来源声明，没来源落保守档"。

2. Temperature / top_p / 采样参数

影响确定性；评测时温度越高越需要重复次数；结构化输出场景常用 0。

面试知识：本项目没有暴露 temperature 配置——真实模型批次的可复现性因此受限（诚实答案）。生产化应把采样参数纳入 TaskSpec/manifest（现在纳入的是 profile、max_rounds、预算）。

3. Structured Output

三种做法：JSON mode、function calling、约束解码。陷阱：模型截断（finish_reason=length）时 JSON 不完整、参数是字符串不是对象、多余自由文本。

本项目落点（代码事实）：用 native function calling（openai_client.py）；参数非法 JSON → 包成 {"_raw":...} 并计 tool_arguments_invalid；截断且仍有 pending tool_call → 硬失败 ModelResponseError，但带 usage 信封——因为钱已经花了。

面试知识：JSON schema 校验 + repair retry 的通用套路；本项目 MAX_PROTOCOL_REPAIRS=1（plain_loop.py）。

4. Function/Tool Calling vs MCP

Function calling = 供应商协议里的"模型输出结构化调用意图"，执行由你的运行时做；MCP = 工具/资源/提示的跨进程标准协议（client-server，可插拔），解决的是生态复用而不是模型能力。

本项目落点：手写 REGISTRY 产 OpenAI function schema，"可见 == 可执行"用同一份白名单（registry.py + plain_loop.py）。

面试知识：如果要把 16 个工具做成 MCP server，需要处理的是生命周期、鉴权、以及"阶段白名单在 server 侧还是 client 侧"——我会坚持放在 client 侧，因为可见性是我安全模型的一部分。

风险点：别说"我用了 MCP"。没有。

5. Prompt Engineering vs Context Engineering

前者写指令，后者决定每一次请求里真正出现什么。AI 应用的效果差异大多来自后者。

本项目落点（代码事实，很好的差异化素材）：三阶段装配（骨架→大纲→观测）+ 按 (stage, round_no) 幂等缓存 + 优先级"平台规则 > 用户约束 > 仓库说明" + 工作记忆只传平台观测不传模型自述 + 观测带 staleness 与 read_evidence 回取指针 + 超限明写省略了多少行、保留哪些行号区间。

B. Agent 机制 #

6. ReAct

Reason + Act 交替：思考 → 调工具 → 观察 → 再思考。它的失败模式是循环、观察误读、过早终止。

本项目落点：plain_loop.py 的回合循环就是 ReAct 的受控实现；finish 做成伪工具让"终止"成为一次显式动作（registry.py、plain_loop.py）。

7. Agent vs Workflow

判据：下一步由模型决定还是由代码决定。Workflow 可预期、可审计；Agent 灵活但难保证终止。

本项目落点：见 02 M2 —— "Workflow 定阶段，Agent 定动作"，8 个 route_* 全硬编码。这道题你必须答得干脆，犹豫就会显得不理解自己的架构。

8. Agent State

状态 = 每一步读写的事实集合。设计要点：可序列化（才能 checkpoint）、无隐藏对象、字段有 owner。

本项目落点：TypedDict total=False（state.py），无 reducer → last-write-wins；不可序列化对象放闭包 TaskNodes。

面试知识：LangGraph 的 reducer/append 语义（Annotated[list, operator.add]）——本项目没用，因为阶段间是覆盖语义不是累加语义。这是被追问时的准确回答。

9. Memory

区分三种：会话内短期（消息历史）、任务内工作记忆（跨阶段观测）、跨任务长期（用户偏好/知识库）。

本项目落点：TaskMemory 是任务内跨阶段工作记忆（task_memory.py），且严格区分"平台观测"与"模型假设"（后者必须带引用，自称已验证被拒）；没有跨任务记忆。

风险点：不要把 SessionState（消息序列修复，session.py）说成 Memory。

10. Termination

Agent 必须有多层终止：最大步数、墙钟、预算、无进展检测、人工中止。

本项目落点（代码事实，这是你最该背熟的一条链）：max_turns=20/回合 → task_timeout_seconds=900 + 绝对寿命 86400s → token/cost/calls 账本 → 无进展检测 = 失败签名 streak（≥2 提示换思路、≥3 收敛 NEEDS_REVIEW）→ recursion_limit=5N+8 图级 → TaskCancelled 协作式（回合边界 + 命令轮询，>5s 才升级为 cancellation_pending）。

11. Infinite Loop / Repeated Tool Call

根因通常是"反馈不可比"（看不出是同一个失败）或"失败信息不足"。

本项目落点：failure_signature = kind + 首行空白折叠[:160]（pytest_adapter.py）；签名规则是受保护代码，因为 streak 依赖它稳定。

面试知识：更进阶的做法是"动作哈希去重 + 强制策略变化"（我用了签名，没用动作哈希，可以答出来作为延伸）。

12. Tool Failure 处理

三种：抛穿（任务死）、重试（可能重复副作用）、把失败作为观察喂回（模型决定）。

本项目落点：execute 把所有异常收敛成 ToolResult（registry.py）+ RECOVERY_POLICY 标注 no_rerun/state_check+ 崩溃恢复时孤儿回执带恢复提示。

面试知识：副作用工具的幂等键/去重表是生产做法，本项目只做了 LLM 层重试的互斥，没做工具层幂等。

13. Multi-Agent

真实需求通常是：角色隔离（工具集不同）、上下文隔离、预算隔离、并行。反模式是"对话式群聊"。

本项目落点：roles.py 三套冻结工具集、子任务无 delegate/ask_user ⇒ 深度 1；SubtaskManager 管槽位/并发/父切子预算/独立 ToolContext/独立轨迹/自有工作区；默认 delegation_enabled=False。

面试口径："有界子任务委派，不是 Multi-Agent。"（详见 02 M12）

C. 护栏与可靠性 #

14. Guardrail

输入护栏（分类/黑名单）、动作护栏（白名单/参数校验/审批）、输出护栏（脱敏/格式）、判定护栏（不接受模型自述）。

本项目落点：动作护栏最强（16 个受控工具、候选补丁写入口、七项门禁、阶段白名单）；输入有仓库说明来源/作用域与冻结验收校验，但没有通用prompt注入检测；输出护栏弱（结构裁剪有，仓库说明部分脱敏，工具输出无通用脱敏）。

15. Hallucination（在代码修复场景的特异形态）

不是"编造事实"，而是：引用不存在的文件/符号、给不存在的测试 id、把"我以为跑过"当事实。

本项目落点（代码事实，很精彩）：测试 id 必须唯一解析到 (file, classname, name) 三元组，0 命中=被 deselect、≥2=歧义，都判不过（pytest_adapter.py）；update_memory 自称 verified 被拒；影子模块门禁防"新建同名模块劫持判定"。

16. Retry 的副作用问题

"Retry 可能重复执行副作用"是必考题。答案要素：区分只读/幂等写/非幂等写；非幂等要么带幂等键要么禁止盲重跑。

本项目落点：RECOVERY_POLICY（见 §12）+ SDK/平台重试互斥 + 恢复不重算预算。

17. Idempotency

本项目落点：spec 内容哈希作幂等键 + 唯一索引 + 锁 + 终态先到先赢。

面试知识：fencing token、幂等表 TTL、"幂等键冲突但请求体不同应返回 409 而不是静默复用"（本项目是"同键同体才复用"，逻辑等价，但没显式测异体冲突）。

D. 评测与数据 #

18. 检索 vs 生成分别评估

要素：检索层用 Recall@k / Precision@k / Hit Rate / MRR（金标=应该命中的文档集合），生成层用 faithfulness / answer relevance / citation correctness。混在一起看"端到端准不准"会导致改了检索却看不见收益。

本项目落点：没有向量检索（代码事实），但我有等价分层：localized/strict/coverage 评定位、resolved 评结果（见 05 §4-5）。

面试知识：RAGAS 的三个指标（faithfulness / answer relevance / context relevance）；MRR 计算 = 首个正确结果排名的倒数取平均。被问公式时要能写出来。

19. Chunking / Hybrid / BM25 / Rerank / Metadata Filter

面试知识（本项目全部未实现，但岗位常问）：chunk 策略（固定长度 vs 语义/AST 边界 vs 父子块）、overlap、BM25 稀疏检索、hybrid（RRF 融合）、rerank（cross-encoder 重排 top-N）、metadata filter（预过滤减少召回噪声）、长文档（map-reduce / refine / 引用聚合）、知识更新（增量索引与版本失效）。

本项目可对照的说法："我用 AST 骨架 + rg 文件级预筛 + Python 逐行了断替代了这一整套，因为代码仓库内定位需要精确行号而不是语义相近片段。未实现向量语义检索，也未测量语义召回质量，如果 bug 描述和代码命名对不上，我这层就没有兜底——这正是我要引入 hybrid 检索做对照的原因。"

20. Benchmark 的可信构建

要素：样本代表性、GT 来源独立性、指标分母诚实、重复次数与置信区间、dev/hidden 分集、预登记判据、负面结果记录。

本项目落点：代码事实 有预登记文化（experiment-preregistration-v2、paid-batch-preregistration 含一次停手负面结果）、控制身份 vs 观测结果分离（compare_experiments.py）、指标版本化（METRICS_VERSION=2，v1 缺陷只作显式重算）、可疑好结果的哨兵（report.py）。但样本代表性是零分（3–5 文件合成题 + 回放 embed 答案）。

21. LLM as Judge

适用：无法程序化判定的开放输出。风险：位置偏好、冗长偏好、自我偏好、评分漂移、被输出里的"指令"操纵。缓解：成对比较 + 顺序交换、多裁判投票、锚定样例、与人工标注校准一致性、把裁判输出当信号不当判定。

本项目落点：代码事实 不用 LLM 做判定；最接近的是 propose_acceptance（模型提验收清单 → 平台真跑基线验证 red/green → 人工审批 → manifest 哈希冻结，app/diagnosis/proposal.py）。被问"为什么不用 LLM judge"时答："我不想引入一个不可复现的判定源，我的整个判定链都在证明'结论必须是平台事实'。但我认为生产上应该把它当排序信号用，比如给多个候选补丁排序——那正是 Best-of-N 现在用规则排序的位置。"

22. Badcase Analysis

要素：按终止原因分桶（预算/门禁/验证失败/待审/取消）、按阶段定位瓶颈、区分"能力失败"与"平台失败"、每类留一条可复现轨迹。

本项目落点：代码事实 终态本身就分桶（INVALID_TASK / PATCH_REJECTED / VERIFY_FAILED / BUDGET_EXCEEDED / NEEDS_REVIEW / CANCELLED），轨迹逐工具记 duration_ms/error，报告三态显式（已验证/未运行/不确定）。swe-ablation-evidence-2026-10-07.md 是一次真实的瓶颈定位记录。

E. 服务与工程 #

23. FastAPI 的 async 真相

async def 路由在事件循环上跑；def 路由被丢进 anyio 线程池；同步生成器响应体被 iterate_in_threadpool 包裹（每流占一线程）；依赖注入是 Depends；中间件 vs 路由依赖的鉴权位置差异。

本项目落点（代码事实，见 02 M1）：路由全同步、async def 只在 ASGI 管道、并发靠 ThreadPoolExecutor(2)、SSE 是 0.5s 轮询 DB。

这就是"知道是什么但不一定能解释为什么"的典型条目，务必吃透这段——被问"async 给你带来了什么"时的满分答案在 03 的服务并发风险。

24. SSE

text/event-stream、id:/retry:/event: 字段、断线重连用 Last-Event-ID、心跳防代理超时、背压与连接数上限。

本项目落点：routes.py + events.py，trajectory_events.id 自增号作续传游标（last_event_id 参数）。

面试知识：WebSocket vs SSE 的取舍（单向进度用 SSE 更合适，鉴权与自动重连是它的优势；双向交互才需要 WS）。

25. Redis / Qdrant / Docker / CI-CD

  • Redis：本项目只有锁（03 的 Redis 风险 已详述）。面试知识：缓存三大问题（穿透/雪崩/击穿）、SET NX EX + Lua 释放、Redlock 争议、fencing。
  • Qdrant：代码事实 项目里没有。面试知识：HNSW vs IVF、cosine vs dot vs euclidean、payload 索引与预过滤、limit/offset 与召回一致性。
  • Docker：代码事实 两个 Dockerfile + compose（api+redis，回环绑定），默认executor镜像依赖有限，题目env可自带依赖镜像；CI build 镜像 + 跑 docker 单测（skipif）；uid 漂移有专门实验（ADR-0002、docker-isolation-notes）。
  • CI/CD：代码事实 单 job ubuntu-24.04 + Python 3.11，lint → 全量 pytest → fake 冒烟 → artifact 上传（if-no-files-found: error）。缺：OS 矩阵、覆盖率、部署步骤、真实模型冒烟。

26. Cost / Latency / Quality 三角

面试知识 + 本项目落点：

  • Cost：token_budget、cost_budget_micro_usd（默认 0=不限，是个洞）、pricing.py micro-USD 向上取整、未收录模型 n/a、settled_bill 无来源（代码自述）。
  • Latency：逐工具 duration_ms、llm_timeout_seconds=120、task_timeout_seconds=900；但没有任何 p50/p95 聚合，因为没指标系统。
  • Quality：resolved、终止原因分布、双跑一致性。

必背 trade-off 例子（都在代码里）：① Best-of-N增加候选和成本，质量收益未证明，延迟受并发与工具执行影响，且默认只在 branching_min_token_reserve=30000 富余时才开（config.py）；② 双跑复核提可信度、成本近乎翻倍（verify_double_run）；③ 大输出"先裁剪再落盘 + 可按游标取回"省上下文但增加一次取回延迟（registry.py）；④ 压不动就 context_capacity_exceeded 停下，而不是烧钱反复压缩。

08 · 项目面试题 #

Q1 · Agent 还是 Workflow？ #

平台控制阶段与验收，模型在阶段内自主选工具。LangGraph 编排 + 阶段内 Agent；模型不决定 verdict。

追问：plain？→ 单轮替代驱动，共享循环/工具/验收，不具有 graph 的全部交互恢复能力。

Q2 · 为什么 LangGraph？ #

显式拓扑、阶段边界与 superstep 检查点。恢复正确性仍由平台候选重验、上下文重建和资源账本保证。

追问：不用框架？→ 能实现，plain已有不同编排；不因重复就抹平合法功能差异。

Q3 · resolved 怎么算？ #

非空补丁、失败集全通过、回归全通过、门禁全过、预算内、未取消；开启双跑时一致。

graph 另验当前工作区与冻结候选绑定。模型 finish(success=true) 只完成阶段。

Q4 · 怎么防假绿？ #

具体 JUnit 身份匹配，拒缺失/歧义/skip；门禁禁止改测试/控制文件、影子模块、越界等已知手段。

追问：能防所有恶意仓库？→ 不能。预置伪 JUnit 或过拟合仍是边界，指定测试不等于语义正确。

Q5 · crash 后为什么重跑？ #

旧 verify 布尔不证明当前字节；candidate 校验 → reset/重应用 → 清旧结论 → 重跑门禁/双集。

END 只核对既有报告；缺可信身份拒恢复，不冷启动重授预算。

Q6 · 配置漂移怎么防？ #

TaskSpec 冻结有效策略，执行使用任务配置副本；pytest显式后端/超时，初始账本按冻结预算建。

本轮回归把全局改docker/极小预算/关闭双跑，graph/plain真实pytest链仍按受理契约执行。

Q7 · 账本坏了怎么办？ #

已有文件读不动不能当“没消费”。标unknown、保留文件、阻止新请求，终局不给resolved。

未知用量不是零；不能借恢复把历史消费额度再发一次。

Q8 · 幂等键是什么？ #

完整 TaskSpec hash，包含源码、具体测试/权限、回放、引擎/臂/模型与有效策略；只复用在途同契约任务。

数据库生命周期与引擎report分工不同，取消赢终态后自然完成不能覆盖。

Q9 · 检索是不是 RAG？ #

AST骨架、符号与字面匹配，rg做文件预筛，Python决定行号。无向量库/embedding/检索质量成绩。

追问：语义检索值不值得？→ 需要真实样本对照，当前没有量化收益证明。

Q10 · evidence 和 memory 有何区别？ #

evidence存原始工具事实并分页取回；memory是平台观测索引与模型引用假设。

修改会让引用stale，阶段装配幂等；没有跨任务长期记忆。

Q11 · 仓库说明能改权限吗？ #

不能。说明来自冻结副本、按目录作用域激活，只指导修复；平台白名单、门禁与验收不读它作授权。

规则源有部分脱敏，工具输出无通用秘密过滤，不作prompt注入全面防护声明。

Q12 · Docker 是否真的用？ #

可选且有执行路径/测试，默认local。pytest容器有网络/内存/CPU限制；诊断命令另有PID/no-new-privileges。

custom Docker预检只查daemon，不在宿主导入conftest；真实依赖收集由容器baseline确认。

Q13 · local 隔离到什么程度？ #

物理目录副本和工具路径限制；测试/复现脚本仍共享宿主权限，不能称进程沙箱。

compose socket有宿主控制边界；官方题目镜像和简单pytest执行器镜像的依赖能力不同。

Q14 · 预算能保证绝不超账单？ #

不能。原子预留控制已用/在途/未知；usage和价表估算micro-USD，端点估计误差与实际账单另说。

返回usage先结算再处理工具，超额不能静默resolved，保留已完成验证证据。

Q15 · 子 Agent 会不会跑飞？ #

默认关闭，三角色、单层、工具集合固定，独立会话与父预算切分；没有delegate递归，不能覆盖父验收。

独立fake脚本缺失明确未配置，不偷用父游标、不暗调真实模型。

Q16 · 真实模型跑过吗？ #

有早期快照和历史SWE/消融/重复实验，证据强度不同；含负结果与停手。

当前升级没补跑。见05，不能说“从未执行”，也不能报官方成绩或泛化修复率。

Q17 · FakeLLM 掩盖什么？ #

回放含答案；legacy计划模式给预制文本，会掩盖真实模型协议遵循、规划与检索效果。

strict协议测试验证控制契约，真实模型能力仍需要受限实验。

Q18 · Redis/SQLite 能多实例吗？ #

Redis只做任务锁，SQLite线程锁/单连接按单进程原型设计；没有可靠多实例领取与吞吐证据。

启动Redis连接失败可回内存，运行中故障另有失败边界，不能称分布式队列。

Q19 · 本轮删了什么？ #

无执行调用的_matches_requested wrapper与ErrorResponse；身份判定仍调用共享case_matches，ADR锚点指真实路径。

reset_workspace在plain可达、fold_output有历史脚本调用、legacy_v1是显式契约，所以保留。

Q20 · 如何审查 AI 改动？ #

先追完整调用链与失败路径，再对规范/测试/文档；拒放松门禁或改期望凑绿。

日常verify.ps1快速定向，失败只复现相关项；完整回归交CI。结果附收据，不编造参与比例或固定通过数。

11 · 面试速记 #

一句话 #

PatchPilot 是 Python/pytest 仓库的测试失败诊断与补丁验证原型，重点是平台独立验收和可追溯证据。

执行链 #

TaskSpec/hash → 输入冻结/预检 → 线程池 → graph 阶段（内部共享 plain_loop）→

检索/证据/记忆 → 计划/块补丁 → 门禁/Git → pytest/JUnit → acceptance → report/SQLite。

issue-only 经诊断提议、平台基线复核、可信批准后才能修复。

plain 是单轮驱动，graph 支持多轮候选、交互与恢复；共用验收不等于功能等价。

必须会讲 #

  • resolved：非空补丁、失败集全绿、回归全绿、门禁全过、预算内、未取消；双跑启用时一致。graph 另验候选 hash。
  • 恢复：checkpoint 定位置，loop/session/memory 带上下文，candidate 带补丁，ledger 带消耗；写阶段重验，无身份不冷启动。
  • 资源：已用 + 在途 + 未知持有，回复先结算；费用是估计，不承诺真实账单上限。
  • 上下文：AST/字面检索，无向量库；有界回执与原文分页；平台观测不等于模型假设；无跨任务记忆。
  • 仓库说明：上下文指导，不进权限面。候选写入口 apply_patch；scratch/记忆/问答另有持久写入。
  • 隔离：默认 local，不是沙箱；pytest Docker 有网络/内存/CPU限制，诊断 Docker 另有 PID/no-new-privileges。
  • 幂等：完整 TaskSpec hash，只复用在途同契约任务；Redis 只做锁，SQLite 单进程原型，不宣称多实例可靠领取。
  • 子任务：默认关闭、有界单层角色委派，独立会话与父预算，不能覆盖父验收。

证据与局限 #

离线 FakeLLM 含参考答案，验证控制链不代表修复率。历史真实 SWE/消融已执行并留有记录，

全绿不证明语义等价，可有过拟合。测试总数、代码行数和 CI 状态不背固定数字，引用具体收据与提交。

13 · 三轮模拟面试 #

第一轮 · 业务与架构 #

问：用一分钟介绍。

答：Python/pytest仓库的诊断与补丁验证原型；模型提议，平台门禁/测试/预算验收。graph编排、阶段内Agent。

不能把生产可用、官方跑分或fake修复率放进开场。

问：一次请求走到结果？

答：TaskSpec/hash幂等→custom输入冻结/预检→线程池→graph阶段→检索/证据→计划/块补丁→

门禁/Git→pytest完整身份→acceptance→report/SQLite。issue-only先提清单、复核、可信批准。

问：为什么双引擎？

答：plain单轮替代驱动与graph分阶段多轮编排，共用工具循环和验收；graph交互/候选恢复未在plain实现。

不把不同功能强行说成完全等价，也不把共享loop删成历史教学代码。

问：Docker边界？

答：默认local共享宿主权限；pytest Docker与诊断Docker参数不同，后者另有PID/no-new-privileges。

Docker预检不宿主collect；官方题目镜像不等于官方评测harness。

第二轮 · 判定与失败 #

问：finish说成功就成功？

答：不是。非空补丁、双集、门禁、资源、取消合取；graph再验候选hash和当前attempt。

问：崩在verify后怎么恢复？

答：校验候选/契约/源/基线/资源，复位并重应用，清旧结论，从apply重跑门禁与验证；缺身份待审。

问：账本损坏？

答：保留原文件、标unknown、不重新发额度；新请求拒绝，不能resolved。本轮加强了这条回归。

问：测试全绿有什么漏洞？

答：指定测试可被过拟合，恶意基线可能伪造JUnit；双跑不能证明语义正确或覆盖所有flaky。

问：预算和账单一样吗？

答：不是。预留/结算/未知持有可审计，usage乘价表是估计；不宣传provider账单绝对上限。

第三轮 · 证据与真实性 #

问：真实模型到底跑没跑？

答：有历史SWE与消融/重复实验及负结果；早期快照缺身份，最早两臂跨引擎、样本偏、回归抽样。

当前升级未补跑，不作官方成绩或当前修复率主张。

问：FakeLLM能证明什么？

答：回放含答案，能验证编排和已覆盖护栏；真实Git/pytest验证工具接线，不能验证模型规划/检索/修复效果。

问：本轮清理为什么可信？

答：追调用方后才删wrapper/schema；保留plain可达的reset_workspace和历史脚本用的fold_output。

用真实graph/plain pytest链核对冻结配置，而不是只看ctx字段；保留门禁和测试身份语义。

问：代码是不是自己全写的？

答：如实说明AI协作。Git署名/行数不能推断比例；现场讲自己掌握的契约、失败路径和实际测试收据。
