## 1. 逐条核对结论

- 第 1–2 轮 14 条声称：**全部属实**（数字精确吻合：28 题、14540ms、4 条 PASS_TO_PASS、max_files=5、recursion_limit=4N+8、docker 五项实验）。措辞瑕疵 3 处（registry 实为 7 受控工具+1 伪工具 finish；budget/command 门禁属参数检查而非纯文本；taskkill/USERPROFILE 记录在代码注释而非 design.md §8），均不构成夸大。
- 第 3–4 轮 18 条声称：**全部属实**（行号级命中，含 runs/real 极值 9767ms/41833ms/5071/73466 逐位吻合；核查代理实测全量 pytest 258 passed + 2 skipped / 246.9s）。小注 2 处：「pytest 固定 4 次」仅对单轮成功路径成立；「真模型只跑一次」未提同日 real-trial 3 次试跑。
- **编造 0 条、夸大 0 条。** 唯一被纠正的是面试官侧：简介称「约 118 个测试」，仓库 README 实写「210+ 用例」，实测 260 collected——外部口径过期，非项目问题。

## 3. 链路地图

```
需求 → 【薄弱】定位真实（单机研究工具）但用户面为零；省时收益未量化、无对照
选型 → 【薄弱】结果合理、部分有实验支撑；三处关键取舍无论证记录（无 ADR）
实现 → 【扎实】端到端行号级闭环：状态机/预算/取消/杀树/停机收敛/门禁/攻击样例全有据
验证 → 【薄弱】258 个离线测试证明逻辑与契约正确；但真模型评测仅手动一次、无盲跑、无对照、无压测
效果 → 【断裂】28/28 的「效果」只在自建软题集内自洽，provenance 缺失导致数字不可追溯——对外不可声明
```

## 4. 问题清单

### P0-1 效果证据断裂：自建软题集 + 零对照 = 28/28 不构成效果证明
- 证据：4-Q10「0 rejected 我承认更像评测集太软：单文件、issue 直指模块名，不证明模型强」「candidates 8 道 hard 零实跑」；1-Q2「没有与人工作业的对照实验」。
- 本质：被验证对象（模型+链路）与验证集（gen_bugs.py 内嵌 spec 生成的同源题目）之间存在循环论证；单文件、模块名直指的题目测不出 localize 与多轮修复能力。
- 改进任务：① 把 `bugs/candidates/BUG-C101..C108`（8 道 hard，gen_candidates.py 已备）人工审题转正并实跑；② evals 增加两种对照模式：去 bug 描述盲跑、失败集外测试置绿检查（过拟合探测器）；③ eval-report 模板强制输出分布字段（min/max/分位耗时、token、rounds、rejected/NEEDS_REVIEW 率）而非只有均值与通过率。

### P0-2 真模型评测不可复现、不可追溯
- 证据：2-Q6「28 题批次 provenance/模型名缺失（audit P1-2 承认）」；4-Q11「端到端真模型评测只跑过一次（runs/real，2026-09-18），纯手动」；核查证实 28/28 份 report.json `model_name=''`、provenance 0/28 非空。
- 本质：效果数字无法绑定到模型版本与代码 commit，任何结论（包括 28/28）都不可复现，一周后即成孤证。
- 改进任务：`app/evals/run_single.py` 落盘前强制写入 `{model_name, model_version, git_commit, config_snapshot, started_at}`，缺任一字段拒绝生成 report.json（在 metrics 判定侧加一条结构校验 + 1 个单测）；提供 `scripts/run_eval.sh` 一键重跑+报告 diff。

### P1-3 判定面与被测代码同机（残余风险自认不设防）
- 证据：3-Q8(d)「最脆：verify 与被测代码同机执行……威胁-model §4 自认不防」；4-Q11「audit-2026-09-19 P0-1 实证改 conftest.py 可把失败测试 skip 成绿」；核查确认已部分整改（pytest_adapter.py:54-76 期望 id 判定 + paths.py:13-19 控制面禁改），但 docker 仅是可选项且默认 local。
- 本质：判定地基「只信测试结果」与不可信输入（模型补丁）共处一个进程/一台主机，攻击面永远存在，整改是补丁式而非结构性。
- 改进任务：把 docker 后端从「已接线」推进为「verify 阶段默认」（config 默认值或至少 README/企划书明示推荐）；短期兜底：verify 对同一工作区连续跑两遍 pytest 并比对 junit（时间戳/用例集/结果三元组），不一致即判 NEEDS_REVIEW（+1 攻击样例 ATTACK-009 与对应测试）。

### P1-4 apply 侧软链逃逸无校验
- 证据：3-Q9(a)「apply 侧软链逃逸无专门校验，靠 git 默认不越工作树+任务后弃工作区」；核查全仓 grep "symlink" 零命中。
- 本质：读侧有 resolve+relative_to（paths.py:67-71），写侧靠「git 默认行为」这一未验证假设，防线不对称。
- 改进任务：`app/gitops/patcher.py` apply 前对每个目标路径做 resolve→relative_to 工作区校验（复用 paths.py 现成函数）；新增 ATTACK-009（补丁建软链指向工作区外）+ 对应门禁测试。

### P1-5 并发能力未度量：max_workers=2、无资源配额、零压测
- 证据：4-Q12「池 max_workers=2（service.py:67,74），10 并发即 8 个排队」「local_runner 无任何 CPU/内存限额（grep 零命中）」「SQLite 单连接全局锁（repository.py:58）」「并发压测：一次没做过」。
- 本质：不是要求它能扛 10 并发（定位是单机工具），而是并发上限从未被测过、也没写进任何文档——容量是拍脑袋数。
- 改进任务：用 FakeLLM 写一个 10 并发冒烟测试（任务排队/超时/锁竞争/状态一致性断言）并记录基线数字；把「并发上限与资源模型」写进 design.md §8（现在只有单进程架构描述，无容量声明）；`max_workers` 提为 Settings 配置项。

### P2-6 三处关键选型无论证记录
- 证据：2-Q4「与 AutoGen/LangChain 的对比没有留下论证记录」；2-Q5「『为何不首选 Docker』无专门论证记录」；2-Q6「与 LiteLLM 的对比无记录」。
- 本质：决策可能对，但决策过程不可审计——新人接手或未来推翻时无从参考。
- 改进任务：新增 `docs/adr/` 三篇短 ADR（编排框架、执行后端默认值、LLM 客户端封装），每篇 ≤1 页：背景/候选/结论/反方意见；不改动任何代码。

### P2-7 无上下文压缩，context_tokens 分布未度量
- 证据：3-Q9(d)「token 累计超 200k 在 turn 边界抛 BudgetError；无上下文压缩/摘要机制，这一点目前没有做到」。
- 本质：200k 预算对单文件自建题够用，对真实仓库（多文件 localize）可能一轮就触顶，且现有 28 题测不出这一点。
- 改进任务：eval-report 增加 context_tokens/题 分布字段（数据已在 report.json 中，补聚合即可）；转正 hard 题后观察是否触发 BudgetError，再决定是否设计压缩。

### P2-8 数字口径漂移（118 vs 210+ vs 实测 258）
- 证据：外部简介「约 118 个测试」；README.md:81「210+ 用例」；核查实测 258 passed + 2 skipped。
- 本质：手写数字必然过期；本项目 README 已写 210+ 仍落后实测 48 个。
- 改进任务：README 的测试数字改为「pytest -q 输出即真相」或 CI 徽章/脚本生成，删除具体手写数字；同步更新外部材料。

## 5. 如果只能改一件事

**把「带溯源的真实评测」立起来：转正 8 道 hard 候选题 → provenance 强制落盘 → 重跑一次真模型评测并发布含分布的完整报告**（即 P0-1 + P0-2 合并执行）。

理由：
1. 杠杆最大——五个维度里实现已 4 分、动机受定位选择所限（改它等于改项目定位），唯独「效果可证 2 分」存在一个单点动作能拉到 4 分；
2. 成本最低——题目已备好（candidates 8 道），链路无需改代码，只补落盘字段与聚合字段；
3. 连锁收益最多——hard 题实跑会同时回答「localize 是否真有必要」（软题里 issue 直指模块，localize 等于没被测过）、「200k 预算够不够」（P2-7）、「verify 需不需要默认 docker」（P1-3 的实验依据），并在下一场面试里把「28/28 只是你自己出题」这个必死问题变成「hard 题 X/Y + 全程溯源可复现」。

## 6. 面试元结论

本次面试暴露的不是「实现不行」——32/32 声称属实、行号级可信，这在真实面试里已属罕见——而是典型的**工程强、实证弱**形态：前三轮（动机诚实、选型可指认、实现闭环）都能扛住追问，第四轮（验证效果）整段塌方，且塌方点全部由项目自己的 audit/威胁模型文档预先承认。项目最大的资产是这份自我拆穿的文化；最大的负债是它目前只用于防守（承认不设防），还没用于进攻（主动证明有效）。
