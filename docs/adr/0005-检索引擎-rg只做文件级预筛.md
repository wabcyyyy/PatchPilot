# ADR 0005:检索与符号工具 —— rg 只做文件级预筛,行级权威只有一份

日期:2026-10-07 | 状态:已采纳 | 素材:PROGRESS.md D.6/D.12、M3/M3.6/M2.5

## 背景

审计前的检索是 `needle in line.lower()` 的 Python 子串扫描,无上下文行、无单文件上限、
无排序,全仓零 AST 能力(`ast` 唯一的用处是补丁应用后的语法预检)。
两个缺陷叠加:一是模型只能"全文扫 + 猜",二是——复核时才量化出来——检索与符号查找
**共用了 `list_files` 的 500 条输出上限**当遍历域,于是按路径排序第 500 个之后的文件
对模型彻底不可见。在 9 道已缓存的真实难题仓库上实测:4 道的必改文件落在可见范围之外
(sphinx-7590 的 `sphinx/util/cfamily.py` 下标 631、scikit-learn-12682 的两处 502/903),
而"搜不到"会被模型读成"这里没有"。

## 候选

1. **rg 做权威**:行号、文本、上下文全交给 ripgrep 输出;
2. **纯 Python 加速**:只优化扫描实现,不引外部二进制;
3. **rg 预筛 + Python 定案**(采纳):rg 只回答"哪些文件可能含有这个关键词",
   行级文本/行号/上下文/裁剪只有一条 Python 实现。

## 结论

候选 1 被**差分探针**否证:rg 剥 BOM、只按 `\n` 断行,而 Python 的 `splitlines()` 还按
`\r`/`\x0b`/`\x0c`/`\x1c-`\x1e`/`\x85`/`\u2028`/`\u2029` 断行(`\x0c` 分页符在真实 Python
源码里很常见)。行号错一位,补丁就贴错位置——而"补丁贴错位置"在这个平台上是静默错误,
不是崩溃。候选 2 放弃了大仓库上的速度收益。候选 3 的两侧差异因此只影响"快不快"。

工程要点:

- rg 用 `--files-with-matches` + **显式文件参数**(而非目录遍历):遍历域由我们自己给,
  于是 `SKIP_DIRS`/隐藏文件/`.gitignore` 的口径不可能与 Python 路径分叉;参数表按
  Windows `CreateProcess` 上限分批。实测目录遍历反而会走穿 `runs/`、`.pytest-tmp*`
  等产物目录,一次查询撞 20s 超时——预筛反而比旧实现慢;
- 四条回落:二进制缺席、任一批失败或超时、`regex=True`(Rust 方言 ≠ Python `re`,
  不给模型第二套答案)、范围内含符号链接;
- 一条方向性护栏:预筛报了文件而 Python 一行没命中 → **整仓复扫**。
  宁可慢,不能少给模型证据;
- `_cap_matches` 复刻旧实现"命中数刚好达上限时按后继文件位置判 truncated"的反直觉口径,
  等价性用例钉住,换引擎不会静默改这个位;
- 结构化检索:`find_symbol`(定义跳转,精确同名优先、无精确才前缀)、`describe_file`
  (单文件大纲 + 真实行区间,解析失败是**可用结果**不是错误)、
  `read_file(path, offset, limit)`(limit 与 `max_read_lines` **取小**——
  天花板由 Settings 定,模型传更大只会拿到更少);
- **遍历域与输出体量解耦**:`list_files` 保留 500 条输出上限并新增 `truncated`,
  `search_code`/`find_symbol` 走独立的 `max_search_files=8000`,没搜全时如实给
  `scope_truncated=True`。谎称穷尽仓库的空结论比慢一点危害大得多;
- 消融两臂同步:`ONE_SHOT_TOOLS` 一并加两个新工具——消融变量是"有无测试反馈/有无重试",
  少一边给一边就是把对照臂做成残臂。

## 后果(含反方)

- +:默认参数下输出与迁移前逐字等价(等价性用例 + 存量用例未改),
  而大仓库的必改文件第一次真的可达;
- −:rg 是外部依赖,Windows/容器/CI 上可用性不同——所以它是可选加速器而非语义来源,
  `search_engine=python` 可强制关掉;
- −:`find_symbol` 在大仓库要解析上百个文件,单次调用是秒级(不缓存:补丁会改文件,
  缓存失效比不做缓存更难写对,而错误符号索引直接导致错锚点补丁)。
