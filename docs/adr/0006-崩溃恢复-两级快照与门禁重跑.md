# ADR 0006:崩溃恢复 —— 两级快照,门禁必须在续跑那次重算

日期:2026-10-07 | 状态:已采纳 | 素材:PROGRESS.md D.9/D.10、M6

## 背景

平台早就在写 LangGraph 的 `SqliteSaver` 检查点(逐 superstep 落 `run_dir/checkpoints.sqlite`),
但**从来没有读它**:全仓 `get_state|update_state|resume|replay` 零命中,
`app/graph/checkpoint.py` 的自述直接写着"无崩溃重放路径"。服务重启时
`recover_stale` 把 RUNNING/QUEUED 僵尸一律判 `NEEDS_REVIEW` 并释放锁。
于是"跑了 19 轮定位后进程死掉"的实际代价是**从零开始**——而 Agent 循环的
`messages`/turn 计数/累计 token 全是函数局部变量,连序列化都没有。

## 候选

1. **只补图级**:读检查点、从被打断的节点继续——一个 superstep 之内(即一次阶段内的
   十几轮工具调用)的状态仍然丢失,冷启动整个阶段等于没省多少;
2. **只补循环级**:序列化消息列表——但没人知道"该从哪个节点继续",阶段与轮次的账目会错;
3. **两级**(采纳):A 级序列化 Agent 循环的工作记忆,B 级用检查点定位续跑位置。

## 结论

- **A 级** `app/graph/loop_state.py`:`LoopSnapshot`(version / stage / round / turn /
  messages / 三个累计量 / task_id)落在任务自己的 run_dir(`loop_state.json`)。
  三条硬规矩:①`tmp` + `os.replace` 原子写——崩溃不能留下半份快照被续跑当真;
  ②读侧**宁缺勿信**:版本、阶段、轮次任一不符或 JSON 损坏一律返回"无快照",
  绝不抛异常,退回旧路径;③超过尺寸上限就不写(只记 debug),可选特性不得反过来影响任务。
  写点在 turn 的一致边界(该 turn 的工具回执追加之后);续跑按快照播种并从 `turn_no+1` 继续,
  **不重置轮次上界**——崩溃不能换来更多 turn 额度。
- **B 级** `app/graph/resume.py`:`graph.get_state(thread_id)` 读回 `(values, next, metadata)`,
  重建不可序列化的闭包对象(ToolContext/baseline_commit 按设计不进 state),
  然后 `graph.invoke(None, config)` 从检查点的 `next` 节点继续。
  `recursion_limit` 只顺延**剩余额度**(原上限 − 已烧步数),已烧完就拒绝续跑。
- 服务层分流:`recover_stale` 对"graph 引擎 + 有通过校验的快照 + 抢到既有任务锁"的僵尸
  重新入队续跑;其余(快照损坏/plain 引擎/自定义仓库任务题面无法重建/抢锁失败)
  **与分流引入前逐字相同**地判 `NEEDS_REVIEW`。双恢复拦截复用 `app/storage/locks.py`,
  且刻意不做 `force_release`——强清锁正是"两个进程同时续跑同一任务"的入口。

## 两条不可协商的安全前提

1. **工作区完整性**:被打断的阶段只要能写文件(PROPOSE 及其之后的节点),续跑前必须先把
   工作区复位到基线 commit。块补丁协议的锚点是拿**磁盘实际内容**校验的,
   崩溃残留的半截补丁会让续跑的补丁落到错误位置或静默错位;复位之后由快照重放
   "模型已经说过要做的事",而不是重放"它当时改到一半的文件"。
   只读阶段(LOCALIZE/PLAN)不复位——复位反而毁掉取证现场。
   额度判定必须排在任何复位**之前**:一个最终被拒绝的续跑不该先把崩溃现场抹掉。
2. **门禁必须重跑**:恢复只带回升阶时的工作记忆,绝不带回任何判断。
   apply 门禁、verify 双测试集、E3 双跑一致性复核、最终 verdict 全在续跑那次真实重算;
   用例按事件计数证明(恢复路径上 `apply_gate`/`verify_double_run` 事件 ≥ 1)。

## 后果(含反方)

- +:长任务不再因为一次崩溃从头再来;检查点从"留档"变成承重结构,
  之前的写盘开销才真正换来收益;
- −:续跑的正确性依赖"阶段边界 + turn 边界"两个一致点,跨这两点的崩溃退化为
  重跑当前 turn(丢一次工具调用的观察),不是丢整个任务;
- −(反方,如实):恢复要求能重建 `BugTask`。自定义仓库任务的测试集不在 tasks 表里
  (`issue_text` 还截到 500 字符),无法忠实重建 → 这类任务**不续跑,判死**。
  宁可判死也不靠猜题面换取"看起来能续";
- −:测试里续跑会真的起一次执行,必须排空线程池,否则后台线程与后续用例抢
  `get_settings()` 缓存(本夜在全量套件里就撞过一次假失败)。

## 验证锚点

- `app/graph/resume.py:1` — `B 级接线`
- `app/graph/checkpoint.py:3` — `恢复分两级`
- `app/api/service.py:7` — `重新入队按检查点续跑`
- `app/graph/loop_state.py:120` — `def load_loop_snapshot`
- `app/graph/plain_loop.py:194` — `resume_snapshot(M6 A 级恢复)`
- `tests/test_resume_crash.py:1` — `真·进程死亡`

用例面(非行锚):`tests/test_resume.py::test_recover_stale_without_snapshot_is_byte_identical_old_path`、
"拒绝续跑不得先毁掉崩溃现场"与"只顺延剩余额度"两例、
`tests/test_loop_state.py`(版本/阶段/轮次不符、损坏 JSON、原子写半途崩)。
"进程真的被杀掉"这一条单独由 `tests/test_resume_crash.py` 承担:崩溃方跑在子进程里、
以 `os._exit` 死亡(不走 `finally`、不关 SqliteSaver 连接),续跑由另一个进程发起 ——
异常型崩溃用例里那些清理动作会被执行,证明不了连接句柄随进程死掉之后检查点仍可重开。
