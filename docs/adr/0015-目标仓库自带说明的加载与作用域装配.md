# ADR 0015:目标仓库自带说明的加载与作用域装配 —— 规则能指导,不能授权

日期:2026-10-11 | 状态:已采纳 | 素材:SPEC §7 G08、验收矩阵 T13、`docs/PatchPilot修复Agent升级SPEC-2026-10-10.md` §1 缺陷清单,`docs/adr/0013`(阶段装配面)、`docs/adr/0014`(窗口与容量口径)

## 背景

被诊断的仓库经常已经写着"给 Agent 看的规矩":`AGENTS.md` 里说"不许动 tests/""这类改动必须
带回归""日期解析要保持 None 语义"。平台从来没把这些字送进请求 —— 模型只能靠**撞上门禁**
才知道规矩,而撞上门禁的代价是一轮真实请求加上一次失败的补丁。

同一件事在本仓库自己身上演示过:本项目的 `AGENTS.md` 写着 basetemp 不许落在仓库内、
七个禁区目录不许引入未讨论的语义变更。如果 PatchPilot 的 Agent 去修一个有这类约定的仓库,
它今天看不见这些约定。

## 候选

1. **让模型自己找**:提示它"先读 AGENTS.md"。拒绝 —— 它不知道要找(提示里没有这条),
   找的时候消耗一轮请求,而且"读到了"和"这条属于哪个目录"两件事都没有读数。
2. **把仓库里所有 `*.md` 拼进 system**:拒绝 —— 体量与注入面都失控(README、changelog、
   第三方文档一起进来),而"哪些是给 Agent 看的规则"这件事本身就是项目约定,不该由平台猜。
3. **平台从冻结输入副本按固定文件名加载,按作用域装配,优先级低于平台规则与任务约束**(采纳)。

## 结论

- **文件名清单是显式的项目 profile**:`FILENAME_PRIORITY = ("AGENTS.md", "CLAUDE.md")`。
  同一目录只取最高优先级那一份;低优先级那份**记成"未纳入 + 原因"**,不是悄悄消失。
  扩充清单要改这一处并补测试,不做"扫到相似文件名就算"。
- **作用域按平台观测进场**:根说明开局就在;目录说明只有当 G06 的记忆里存在该目录(或其内部)
  的**真实观测路径**(read_file / describe_file 那一条)才进场。用观测而不是"模型说它要改谁":
  观测是已经发生的事,自述要到计划之后才有。
- **超限必须明写**。单文件超 `repo_instructions_max_file_bytes`(默认 16 KiB)⇒ 截断,
  块里写"另有 N 字节未显示,原文共 M 字节",并且**退回完整行首**再显示(裁在行中间等于给模型
  半条指令);总量超 `repo_instructions_max_total_bytes`(默认 64 KiB)⇒ 整份不纳入,块末点名
  "未纳入的说明:路径(原因)"。
- **边界一律复用现有实现,不写第二份**:越界判定走 `paths.relpath_within`,忽略集合走
  `files.SKIP_DIRS`(`.git`/`__pycache__`/`node_modules`/`.venv`),二进制拒绝走 `looks_like_text`;
  符号链接一律拒绝且不跟随。SPEC §7 给这几个文件的定位是"只保留或强化现有边界",
  本卡对它们**零改动** —— 出现第二份边界实现才是风险。
- **形似凭据的行在渲染前打码**。装配文本会进 `loop_state.json` 与轨迹,而轨迹经
  `GET /tasks/{id}/trajectory` 原样对外(T24)。哈希与 digest 仍按**原始字节**算:
  打码是显示层的事,不许动内容身份。
- **每份说明留四件读数**:相对路径、sha256、作用域、裁剪(显示了哪些字节),
  一起进 `repo_instructions_loaded` 轨迹事件;`digest()` 是"路径 + 每份完整哈希"的哈希。
  运行身份不需要新机制:说明文件本身就在 S06 冻结副本里,改一字节 `source_snapshot_hash` 就变
  (有用例钉住这条)。
- **T13 是结构保证,不是提示词礼貌话**:工具 schema 来自注册表 + 阶段白名单(`tool_schemas`),
  门禁来自 `paths.py` 的判定,验收来自 `acceptance.py` —— 这三条路径都不 import 这一层。
  说明块只是 `extra_system` 的一段文本。用例分别钉:①规则里点名的 `run_shell` 不会出现在
  可见 schema 里;②有没有说明,同一阶段的 schema 逐字节相同;③块头明写
  "平台硬规则 > 用户明确任务约束 > 这些仓库说明"。
- **装配顺序 = 说明 → 骨架 → 记忆**。前两者对一个任务稳定,记忆随观测增长;
  把易变的放末尾才不会每阶段重写前面的 stable prefix(G06 的幂等装配同一口径)。

## 代价与反方

- **只认两个文件名是选择,不是通用能力**。`.cursorrules`、`docs/contributing.md` 这类约定
  不进场;这是故意的(候选 2 被拒的理由),但要知道边界:一个把规矩写在 README 的仓库,
  这一层帮不上。
- **作用域按观测进场 ⇒ 没碰过的目录的规则永远不在场**。这把"全仓注入"的风险换成了
  "漏约束"的可能:模型如果不去读那个目录,那条约束就没进过请求。目录级说明与
  `allowed_paths` 的交集(受理时就知道目标目录)是更紧的做法,本卡没做,登记给后续。
- **同目录只取一份就是会丢一份内容**。CLAUDE.md 与 AGENTS.md 同时存在时后者不进场(带原因)。
  合并两份会带进互相矛盾的指令,而矛盾由谁裁决不该由平台在运行时临时决定。
- **64 KiB 的默认档没有标定**。真实仓库的 AGENTS.md 可能一次吃掉半个软窗口,挤掉的正是
  G07 抬起来的目标窗口与 G06 的记忆块。三个字符档(骨架 / 记忆 / 说明)现在各管各的,
  缺一个统一的分配器 —— 这条与 G05/G07 登记的"联动标定"欠账是同一件事,仍待真实端点读数。
- **说明内容不被解析也不被校验**。恶意或过期的规则原样在场(只是不被执行);平台不判
  "这条规则与门禁冲突",冲突时以块头那句声明 + 门禁的实际拒绝为准。这意味着模型仍可能
  先按规则试一次再被挡 —— 省掉的是一部分轮次,不是全部。
- **plain / one-shot 引擎不接这一层**,与仓库骨架同一口径(它们的 `extra_system` 从来不注入)。
  同一份规则在两条路上作用不同,做两臂对照时这是个未登记差异,要么两边都关,要么只看 graph 臂。
- **子任务(G13)的"继承适用规则的已冻结引用"没做**:今天没有子任务运行面。
  实现时必须带 digest 一起传,否则"继承了规则"这句话无法验证。
- 离线全绿只证明**装配与边界**:不证明带上规则能提高修复率、不证明减少撞门禁的轮次。
  那要真实批(G17)。
