# ADR 0004:上下文分层 —— 持久记忆、工作记忆与滑动窗口压缩

日期:2026-10-07 | 状态:已采纳 | 素材:PROGRESS.md D.1-D.5、runs/swe-hard-graph* 付费证据

## 背景

修复一个仓库级缺陷需要模型读很多文件,而"读过的东西"会一直留在请求里。
审计前的实现只有一个消息列表(`plain_loop.py` 里唯一的构建点),**从不裁剪**:
上下文只增不减,超预算的唯一出口是 `BudgetError`。付费实跑把这个缺陷放大成主死因——
多文件题光靠 LOCALIZE 的只读调查就烧到 417,894 tokens(份额顶 400k)、
`apply_patch` 0 次(两次独立跑法同形)。同时,仓库结构(文件树/模块大纲/符号)
**从未进过提示**,模型只能自己 `list_files` 现场重建。

## 候选

1. **只提预算**:抬 `token_budget` 与轮次上限——被证据否证,已烧的 400k 不是上限不够,
   而是历史里绝大多数内容是"我已经看过的那份文件";
2. **LLM 语义摘要**:周期性再发一次请求把旧历史压成摘要——多一次花费与一次不确定性,
   且摘要本身可能丢掉补丁需要的锚点上下文;
3. **分层 + 机械压缩**(采纳):持久记忆(系统设定 + 仓库骨架)固定在场、
   工作记忆(工具轨迹)按软阈值压成存根,必要时整组丢弃。

## 结论

三层形状:

- **持久记忆** `app/context/repo_map.py`:stdlib `ast` 本地生成"文件树 + Python 符号大纲",
  零请求注入 LOCALIZE/PLAN/PROPOSE 的系统层。大仓库(文件数 > `repo_map_max_files`)
  结构档自动换成**目录级汇总**——"字母序前 200 个文件"对 1900 文件的仓库是只画了角落的地图,
  而模型会当成全图决策;截断必须对模型可见(`… skeleton truncated` / 取样说明行)。
  骨架是**优化项**:外壳吞掉一切异常返回空串,可选上下文块没有资格把任务打成失败。
- **工作记忆** `app/context/token_window.py`:turn 边界按 `context_window_tokens` 软阈值压缩。
  不可压区 = system + 首条 user + 最近 `context_keep_recent_turns` 个回合组。
  Pass A 把更早的 tool 结果换成**带工具名与关键入参**的单行存根(反查 `tool_calls` 的
  `tool_call_id`)——只删内容不告诉模型"查过什么",等于教它把同一个文件再读一遍;
  仍超量才有 Pass B 整组丢弃,assistant 与其 tool 回执同进同出(不留孤儿消息)。
  `reasoning_content` 压成占位但**不删字段**(思考模式端点缺它就 400,见 `4a4093e`)。
- **跨阶段通道**保持文本(`findings` / `feedback` / `plan`),阶段之间仍是新会话——
  这样每个阶段的额度可核算,也让 FakeLLM 回放继续可用。

压缩发生在预算检查**之前**,门禁本身一字未改:压缩只让"发出去的内容"变小,
不放宽任何额度,压完仍超预算照旧 `BudgetError`。

## 后果(含反方)

- +:同样的额度能走更多有效轮次;持久记忆让"该改哪个文件"从模型的 turn 里挪出来;
  压缩是确定性纯函数,可单测、可离线复现,零额外花费;
- −:机械压缩**不区分内容价值**,被压掉的可能是后来要用的细节——补偿是存根保留
  "查过什么"、pinned 尾部、以及 M5 的计划工件把结论显式化;
- −(反方,必须一起读):`context_window_tokens` 的默认值目前是**工程判断而非实测结论**。
  FakeLLM 无视消息内容(`ADR-0003` 自认),零成本回放照不出压缩对真实模型的效果;
  要证明"压缩提高解决率"必须真实模型批(人工授权)。因此这两键都进 provenance
  快照白名单:同题开/关压缩的轨迹不可比。
- **(2026-10-08 M15 实测补充,不改本篇结论)**:第一次拿 25 份真实模型 run 离线量了这条阈值的
  **额度**表现(零成本、静态动作序列反事实,`scripts/context_replay.py` +
  `scripts/measure_context_counterfactual.py`,原始输出在 `docs/evidence/2026-10-08-context-*.txt`)。
  三条事实:①阈值是估算口径的,`len//4` 在真实语料上低估约 **1.47 倍** ⇒ 16000 实为 ≈23,500 真 tokens;
  ②16000/keep=6 在触发实例上的累计额度节省中位只有 **6%**,而要省到 31% 得 8000+keep=4,
  那时 52% 的压缩回合"压不到位"——**阈值与 keep 联动**,本篇默认组合的实际含义是"几乎不动杠杆";
  ③锚点代价可量:42 个"金补丁文件全文可见"项在生产阈值下丢 1 个(8000 下丢 3 + 降级 1),
  且压缩后的请求形态 0 条孤儿 tool 消息。
  **仍未证明的还是那句老话**:这些是额度与形态证据,不是解决率证据——本篇结论不变。
- **(2026-10-08 M17 补充,仍不改本篇结论)**:同一批语料顺带量出了**顺序**为什么必须保持。
  额度门禁比的是"provider 真值累计 + 本地估算的待发请求"两个单位,估算低估 1.47 倍 ⇒ 系统性晚判死;
  新增的 `Settings.token_estimate_factor`(`app/graph/plain_loop.py:313` 的 `pending`)乘的是
  **压缩之后**的那个估算 —— 所以"压缩排在预算检查之前"这条设计仍然成立:先给工作记忆一个公平的机会
  变小,再用同一口径判死。若把换算挪到压缩之前,"能压下来也照旧死"就回来了。
  默认 1.0 = 不换算,本篇描述的语义逐字不变(取值待真实批决定)。
