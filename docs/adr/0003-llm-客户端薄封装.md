# ADR 0003:LLM 客户端 —— 只统一 Model 协议的薄封装

日期:2026-09-25 | 状态:已采纳 | 素材:interview-audit-2026-09-24.md 2-Q6

## 背景

平台对模型层的全部需求:一个同步补全面(complete),带超时/重试/token 计量;
另有一个零花费、确定性的 FakeLLM 回放实现支撑离线评测与测试。
审计 2-Q6 承认"与 LiteLLM 的对比无记录"。

## 候选

1. **LiteLLM 统一网关**:多 provider 路由/费率/缓存一站式;
2. **自研协议层**:自己实现 OpenAI 兼容协议、重试、流式;
3. **官方 SDK 薄封装**(采纳)。

## 结论

只统一 `Model` 协议(provider/model/complete),传输、重试、超时全部委托
官方 openai SDK(Settings.llm_max_retries/llm_timeout_seconds 直接透传)。
理由:平台用不到 LiteLLM 的路由/费率/缓存语义,引入它是纯增的依赖面与可错层;
自研协议层则要跟着各端点的兼容性变化走。成本统计在平台侧自持
(pricing.py + price_overrides),不依赖网关记账。

FakeLLM 与真模型同协议(provider=fake-replay),保证全量测试与 fake 批次
零花费、可离线、确定性。其边界如实记录:P1-1 注释自认"回放无视消息内容,
照不出 PROPOSE 阶段的盲改"——盲跑对照(--blind,E6)只作冒烟口径,
真实效果证据必须来自真实模型批(人工触发,见夜间 SPEC §4 清单)。

## 后果(含反方)

- +:依赖面最小;SDK 的重试/超时语义随官方维护而正确;
- −(反方):将来接入第二家 provider 时要逐家写适配(LiteLLM 一层搞定);
  若需要跨 provider 的预算/费控中心化,现设计要补一层网关——届时重评,
  当前单端点现实下不预支该复杂度。
