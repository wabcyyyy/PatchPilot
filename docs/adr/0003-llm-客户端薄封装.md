# ADR 0003:LLM 客户端 —— 只统一 Model 协议的薄封装

日期:2026-09-25 | 状态:已采纳 | 素材:interview-audit-2026-09-24.md 2-Q6

## 背景

平台对模型层的全部需求:一个同步补全面(complete),带超时/重试/token 计量;
另有一个零花费、确定性的 FakeLLM 回放实现支撑离线评测与测试。
审计 2-Q6 承认"与 LiteLLM 的对比无记录"。

## 候选

1. **LiteLLM 统一网关**:多 provider 路由/费率/缓存一站式;
2. **自研协议层**:自己实现 OpenAI 兼容协议、重试、流式;
3. **官方 SDK 薄封装**(采纳)。

## 结论

只统一 `Model` 协议(provider/model/complete),传输、重试、超时全部委托
官方 openai SDK(Settings.llm_max_retries/llm_timeout_seconds 直接透传)。
理由:平台用不到 LiteLLM 的路由/费率/缓存语义,引入它是纯增的依赖面与可错层;
自研协议层则要跟着各端点的兼容性变化走。成本统计在平台侧自持
(pricing.py + price_overrides),不依赖网关记账。

FakeLLM 与真模型同协议(provider=fake-replay),保证全量测试与 fake 批次
零花费、可离线、确定性。其边界如实记录:P1-1 注释自认"回放无视消息内容,
照不出 PROPOSE 阶段的盲改"——盲跑对照(--blind,E6)只作冒烟口径,
真实效果证据必须来自真实模型批(人工触发,见夜间 SPEC §4 清单)。

## 计量协议修订(G02,2026-10-11)

上面那句"传输、重试、超时全部委托官方 SDK"在**计量**维度上不再成立,现在的实际形状:

- usage 的解析排在 choices / 工具参数 / finish_reason 的业务解释之前;结构解释失败仍抛异常,
  但异常带着已知消耗(`ModelResponseError.envelope`),循环先入账再收尾。此前空 choices、
  截断的补丁这两条路径都把"已经花掉的钱"读成 unknown,账本与报告看不出这笔花费;
- 用量来源只有 `provider | estimated | unknown` 三种,账本 `record_usage` 的默认 provider
  标签在消费处被取消——回放脚本与字符估算不再冒充端点真值;
- SDK 的隐式重试(`llm_max_retries > 0`)发生在一发 `create()` 内部,平台看不见次数,
  只能如实记 `retry_owner=sdk_opaque` 与上界,**不补造历史用量**;
- 平台显式重试(`TransportRetryPolicy`)要求 `llm_max_retries=0`,两者同时配置在构造处直接拒绝:
  两层重试会让同一笔消耗无法对账。每次物理尝试有独立 ID、自己的用量读数与失败状态;
- 缓存明细(标准 `cached_tokens` 与 DeepSeek 风格 `prompt_cache_hit/miss`)永远是 prompt 的子集,
  入账总额不含它;两套写法同时存在且不一致时按较小的 cached 入账并登记异常。

范围边界:`app/llm/profiles.py` / 运行 profile 的装配点是 G07 的声明范围,本篇只落地"机制 +
用例";`TransportRetryPolicy` 目前没有生产调用方,这是刻意的,不是漏接线。

## 后果(含反方)

- +:依赖面最小;SDK 的重试/超时语义随官方维护而正确;
- −(反方):将来接入第二家 provider 时要逐家写适配(LiteLLM 一层搞定);
  若需要跨 provider 的预算/费控中心化,现设计要补一层网关——届时重评,
  当前单端点现实下不预支该复杂度。
- −(G02 之后新增的反方,必须一起读):计量协议在平台侧多了一层 envelope,**离线用例只证明
  "读数说了什么"**,各端点 cache 字段的真实计费口径、以及"重试是否真的少花钱"都没有在线证据
  (G17);把 envelope 的 estimated 读数当成账单来停手,是超出本篇证据的做法。
