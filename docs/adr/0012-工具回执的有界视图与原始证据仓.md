# ADR 0012:工具回执的有界视图 —— 裁在序列化之前,原文落进任务证据仓

日期:2026-10-11 | 状态:已采纳 | 素材:SPEC §7 G05、§1 缺陷 4、评审 `agent-readiness-review-2026-10-10.md` R4、`docs/evidence/agent-upgrade/probe-after-g05.json`

## 背景

`run_plain_loop` 把工具结果发给模型前做了两步:`json.dumps(payload)` → `fold_output(content, head=40, tail=15, hard_cap=8000)`。
头尾"行"折叠的前提是文本真的多行,而 JSON 里源码的换行是 `\n` **转义字符**,整份回执通常是**一行**
——于是折叠立刻退化成 `folded[:8000] + "... (truncated)"`(PROGRESS D.5、`context_replay.py:274` 同记)。
两层后果都在本地量过(零模型,素材是缓存的真实上游仓库源码,`read_file` 的 400 行窗口):

| 真实回执 | 原文字符 | 旧路径 | 新路径 |
|---|---|---|---|
| sphinx-75900 `sphinx/util/cfamily.py` | 13,425 | 8,013 字符,**`json.loads` 失败**,5,410 字符无痕迹消失 | 2,457 字符,合法 JSON,标注省略 345 行与保留行号区间,原文逐字节可取回 |
| astropy-87070 `astropy/io/fits/card.py` | 16,473 | 8,013 字符,**非法**,8,458 字符丢失 | 2,174 字符,合法,省略 344 行,可取回 |
| pylint-69030 `pylint/lint/run.py` | 8,690 | 8,013 字符,**非法**,675 字符丢失 | 2,612 字符,合法,省略 177 行,可取回 |
| requests-11420 `requests/adapters.py` | 7,331 | 未超限 ⇒ 原样 | 未超限 ⇒ **一字不变**(不加任何键) |

收据:`docs/evidence/agent-upgrade/probe-after-g05.json`(sha256 前 16 位 `bf63af592b2d64f6`,
可 `scripts/probe_g05_bounded_view.py` 重跑,零模型零网络)。

旧路径的失败方式对 Agent 尤其坏:模型收到一段缺尾括号的 JSON,它既不能解析也不能判断"是没查到还是被切了",
只能重发同一查询——而重发就是又一轮请求、又一份额度。这个形状在付费批里出现过
(`runs/swe-hard-graph*` 的 LOCALIZE 反复重读同一文件,当时归因于缺线索,现在看**可见面本身也不可信**)。

另外 `git_diff` 自己带了一把 `[:20_000] + "(truncated)"` 的刀:同一份信息两套裁剪器,
而且被它切掉的 diff 尾巴既没落盘也不可取回。

## 候选

1. **把 hard_cap 抬高**(如 32k):超限概率下降,但结构损坏与无痕丢失的机制一个字没改,只是更晚发生;
2. **`json.dumps(..., indent=2)` 让折叠真的有行**:JSON 合法了,但"切在第 N 行"仍是无声丢失,
   模型还是不知道后面还有什么;
3. **序列化之前在数据结构上裁 + 原文落盘 + 分页取回**(采纳)。

## 结论

- **裁在数据结构上,不在字符串上**(`output_filter.bound_structure`)。两阶段、顺序固定:
  先按行折长字符串(信息密度最高的地方),仍超限才开始丢列表尾巴(整条整条地丢)。
  顺序反过来会让一条 400 行的 `read_file` 把 50 条检索命中全挤掉。发出去的一定是合法 JSON。
- **原文一律落盘**(`app/context/evidence.py`):`<run_dir>/evidence/<随机 id>.json` + `index.jsonl`,
  与 `ledger_state.json` 同一个 run_dir 口径。模型可见的那一屏拿到
  `_bounded`(可见上限、原字符数、省略行数、丢了几个列表项、哪些字段被折)与 `evidence`
  (id、来源、`workspace_revision`、raw hash/字节/行、`retrievable`)。
- **取回是新工具,不是内部函数**:`read_evidence(evidence_id, cursor, limit_bytes)`,
  进 `READ_TOOLS`/`WRITE_TOOLS`/`ONE_SHOT_TOOLS`(两臂同时在场,理由见下"代价")。
  id 是随机 hex 且必须先命中**本任务**索引 ⇒ "ID 映射成宿主路径"与"读别的任务"两条路都不存在;
  未知 id 与他任务 id 得到同一个 `not registered in this task` 读数,不给存在性旁证。
- **游标钉在工件上**:`<字节偏移>:<内容 hash 前缀>`。格式不对、偏移越界、把 A 的游标拿到 B 上用,
  各自单独报错;预算内才对齐行尾,装不下的长行切在中途并写 `line_aligned=false`。
- **引用带工作区代数**:`ToolContext.workspace_revision` 由 registry 在 `apply_patch`/`reset_workspace`
  成功时 +1(写工具集合只在这一处定义)。代数与当前不符时 `stale=true` 且明说"不能当现状用"——
  旧证据可以取回,但不能被读成现在的代码。
- **落盘失败必须明说**:单工件超体积上限或总量超配额时**拒绝落盘**,回执写 `retrievable=false` + 原因,
  证据仓关闭时写 `raw_saved=false`。任何"裁了但没留"的状态都不得伪装成"没裁"。
- **只在真裁过时改形状**:装得下的回执形状一字不变,存量轨迹与两臂对照解析的形状不受影响。

## 代价与反方

- 模型可见的一屏从 8,000 字符降到 2,174–2,612 字符(见上表)。**这是形状变化,不是能力提升**:
  可见行数现在由 `refine_head_lines`/`refine_tail_lines`(40+15 行)决定,而不是由 cap 的字符数决定
  ——同一份回执在旧路径下是"8,000 字符但读不懂",新路径下是"55 行但读得懂且原文可取回"。
  G07 要把软窗口抬到 64k 时,这两个键必须一起标定,否则窗口变大而每条回执仍是 55 行。
- 多了一条模型能力(`read_evidence`)与一条轨迹事件(`evidence_bounded`),token 与取证面都变大一点;
  分页读回的文本本身也占上下文,所以 `evidence_page_bytes` 默认 4000(小于可见上限,不会自相矛盾)。
- **两臂对称是刻意的**:消融变量只允许"有无执行反馈/有无重试"。把 `read_evidence` 只给一臂
  等于私自给另一臂加 handicap —— 这条教训在 `swe-hard-oneshot` 批上已经花过 777k token 买过一次。
- **原始 stdout/stderr 的全量落盘不在本篇**:`local_runner` 仍只保留末 `max_output_chars=20_000` 字符
  (`_truncate` 取尾不取头)。命令类输出进证据仓是 G09 `CommandProfile` 的范围,那里才有
  "一次执行的完整 stdout 是工件"的契约。本卡只保证**工具回执**这一层不再无痕丢失。
- 离线全绿只证明协议与形状,**不证明修复率**:更少重查、更快收束是待验证假设,属 G17。
- 上限取值(8000 / 2 MiB / 64 MiB / 4000)是工程起点,不是标定结果;`evidence_max_total_bytes`
  对超长任务够不够,只有真实批能回答。
