# ADR 0009:严格验收契约 —— 终局共享验收、资源账本、恢复证据绑定

日期:2026-10-08 | 状态:已采纳 | 来源:docs/PatchPilot执行SPEC-2026-10-08.md §3(F1–F5 审查证据)

## 背景

外部审查(2026-10-08,PatchPilot-review.md)在基线 `442cd8d` 上复现了两组 P0:

- **F1**:plain/graph 两引擎都只在发请求前检查预算;最后一条回复(含 finish)的真实 usage
  入账后循环直接返回,`finish` 节点无条件写 `FINISHED/resolved`——README 承诺
  "未超预算才 resolved",终局却没有兑现这条契约(复现:预算 20000、末回复 50000,仍 resolved)。
- **F2**:恢复把 propose/apply/verify/rollback/finish 之后的工作区一律复位到基线,
  再直接执行检查点的 `next` 节点。next=finish 时补丁已被复位清掉,
  `finish` 仍按检查点里的旧 verify 布尔值判 resolved——磁盘 diff 为空、报告宣称修复成功。
- **F3**:JUnit 匹配只对 file+方法名,请求 `TestA::test_same` 时只有 `TestB::test_same`
  通过也算 all_passed——错误测试身份被验成通过。
- **F5**:apply 节点先预增 round_no 再让 route 用更新值比较,max_rounds=2 的首轮门禁
  拒绝直接跳过第二轮。

真正的 P0 是"错误测试身份被验成通过"与"恢复后补丁消失却仍成功";
单次 API 回复跨阈值不是普遍 P0(mini-SWE-agent DefaultAgent 明确允许下一次调用前才查费用),
但 **README 契约写的是"未超预算才 resolved"而终局不复查**,这是声明与终局不一致,必须收口。

## 决定

### 1. resolved 契约保持严格,新增三个解释维度

`原失败集全通过 ∧ 回归集全通过 ∧ 门禁全通过 ∧ 未超预算 ⇒ resolved`。
本轮**不新增**"超预算也 resolved"的模式;预算超限仍 `BUDGET_EXCEEDED/failed`。
即使验证通过,也不能静默写 resolved。旧 `status/verdict/outcome` 字段保留。

最终验收收敛到 graph 与 plain **共用**的一套 acceptance helper,检查:
当前非空 diff、完整测试身份、门禁结论、双跑一致性(开启时)、资源与取消状态——
不只相信 state 里的两个 verify 布尔值。旧 checkpoint 中的 `verify_*` 布尔值
不能直接作为新执行的验收证据。

报告新增(不替换旧字段):

| 字段 | 取值 | 含义 |
|---|---|---|
| `validation_status` | `not_run / passed / failed / inconclusive` | 已有补丁的验证情况 |
| `resource_status` | `within_budget / exhausted / exceeded / unknown` | 任务资源情况 |
| `gate_status` | `not_run / passed / rejected / inconclusive` | 门禁执行情况 |

- `inconclusive`:双跑不一致、测试身份有歧义或证据不完整;
- `unknown`:有在途模型请求却无法恢复真实用量。不可用 0 代替未知;
- 没有验证过的任务不能因无 gate_violations 而展示"门禁已通过"。
- `report_schema_version=2`;JSON 与 Markdown 报告同源;旧报告缺字段显示 unknown/not_run。

### 2. 资源账本(ResourceLedger)

一个任务只持有一份线程安全账本:实际 total/prompt/completion、模型调用数、
各阶段/分支用量、token limit、deadline、resource_status、停止原因。

- 每次模型调用有持久 `call_id`:请求前记 pending,收到回复**立即**先记真实用量,
  再处理工具或 finish。重复同 call_id 入账无效;不按整份 messages 再收费。
- usage 来源标 `provider | estimated | unknown`;估算不冒充 provider 真值。
  异常/取消/finish/分支失败均保留可知消耗;崩溃留下 pending 且无实际 usage 时标
  `unknown`,保全现场、NEEDS_REVIEW,不把余量重授或已用写 0。
- 请求前保留现有估算检查并为单次输出预留额度;校准系数 1.47 不设为默认
  (与本 ADR 前的 config 注释一致,属真实两臂批的裁决)。
- 回复导致任务超限:记录实际 overrun,停止本回复后续工具调用与新模型请求,
  结构化收尾;**之前已完成的验证可以记录 passed,但严格 verdict 仍失败**。
  阶段份额跨阈值按阶段降级/收敛,不伪装成任务总超限。
- 累计额度覆盖 LOCALIZE/PLAN/PROPOSE、失败调用中可知的消耗与全部分支候选,不只统计赢家;
  任务总额、阶段份额、工具 turn 上限三类上限不互相混用。0=无限的既有约定保留。
- 不新增美元硬门禁;`cost_usd` 继续是带价目表版本的估计值,不冒充实际账单。
  输出无限或无法可靠估算时如实记录能力边界,不宣称"绝不超账单"。

### 3. 时间口径(需与 token 口径分开)

`task_timeout_seconds` 覆盖**从执行线程真正开始到最终验收**的全任务墙钟:
排队不计;恢复停机间隔计入;恢复不重授 900 秒。deadline 在执行启动时建立并持久化,
恢复使用原 deadline 的剩余时间(不依赖跨进程 monotonic 值);
没有可信旧 deadline 的旧快照降级 NEEDS_REVIEW。
每次执行(run_pytest)前检查剩余时间、执行后复查,尤其最后一次 rerun 之后;
剩余时间不足不启动下一次执行。仍用合作式终止 + 执行器超时,不宣称毫秒级强杀。

### 4. 成功必须绑定当前候选和当前验证

验证证据至少绑定
`task_spec_hash / source_snapshot_hash / baseline_commit / candidate_hash / test_policy_hash / verification_attempt_id`;
门禁证据另带 `gate_policy_hash`。最终接受时核对工作区实际 diff 哈希与候选哈希一致,
且证据是当前执行尝试产生的。恢复只恢复输入、候选和进度,**不恢复成功结论**。

### 5. 轮次语义

`round_no` = 当前候选尝试,1..max_rounds;一次 gate 拒绝或一次验证失败各消耗一次候选尝试;
递增只发生在一个位置。成功前允许恰好 N 次候选尝试(max_rounds=2:首轮被拒后
第二轮 PLAN/PROPOSE 必须真的发生)。阶段内 max_turns 含义不变,不把工具 turn 当补丁 round。

### 6. 指标版本

指标语义变更必须带版本号(`metrics_version`):本轮 `localized_strict` 收紧为
`bool(touched) and touched <= expected`(空触碰不再算成功),历史 v1 数值可显式重算,
新旧结果不得放在无版本的同一列;不回写旧成绩。

## 后果(含反方)

- +:README 契约与终局状态一致;崩溃恢复不再复用陈旧成功结论;错误测试身份被拒;
  两引擎终局同一条验收代码,消融对照的判定面不再混杂。
- −:最后一条回复跨阈值时任务判 failed——即便补丁本身验证通过。
  这是契约的代价,不是缺陷;已完成的验证证据保留在 `validation_status` 供复盘。
- −(反方,如实):pending 调用崩缺 usage 时记 `unknown` 而不是 0,
  一批任务的"已用 token 合计"因此不再是严格下界;这是诚实的代价。
  本轮不做 provider 账单对账。
- −:恢复重应用候选会重跑门禁与测试,恢复路径更贵;这是"证据是当前尝试产生的"的必要成本。
