# PatchPilot 项目初步企划书与学习建议

## 1. 项目定位

### 1.1 项目名称

**PatchPilot：面向软件仓库的测试失败诊断与补丁验证平台**

### 1.2 参考项目

- [SWE-agent](https://github.com/SWE-agent/SWE-agent)：Issue 驱动的代码 Agent，提供仓库操作工具、模型工具循环和 trajectory 记录。
- [mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent)：SWE-agent 团队推荐的新一代轻量实现，代码规模更小，适合先理解核心机制。
- [Agentless](https://github.com/OpenAutoCoder/Agentless)：提供问题定位、上下文选择和补丁生成的简化研究路线。
- [SWE-bench](https://github.com/SWE-bench/SWE-bench)：提供标准化的软件修复任务与评测思路。

参考这些项目的工具循环、任务格式和评测方式，独立实现适合应届生理解和展示的工程子集，不声称复刻完整 SWE-agent 或达到 SWE-bench 水平。

### 1.3 一句话描述

给定一个本地软件仓库和测试失败描述，Agent 自动调查相关代码、生成补丁、在隔离工作区执行测试，并根据测试结果和变更范围判断补丁是否可靠。

### 1.4 与 Travel-Assistant 的区分

```text
Travel-Assistant：面向旅行规划的业务 Agent，重点是多轮状态、外部 API 工具和确定性行程变更。
PatchPilot：面向研发流程的开发者 Agent，重点是仓库理解、命令执行、补丁验证、回滚和质量门禁。
```

## 2. 用户使用方式

用户提交：

- 一个本地 Git 仓库或指定 commit；
- 一段 Bug/Issue 描述；
- 测试命令或项目适配器；
- 最大修复轮数和执行资源限制。

系统返回：

- 任务状态和执行轨迹；
- 修改文件和 unified diff；
- 测试前后结果；
- 修复结论：`resolved`、`needs_review` 或 `failed`；
- 失败原因、资源消耗和人工复核建议。

典型示例：

> 仓库中的日期解析函数在输入空字符串时抛出异常，请修复，并保证原有测试和新增回归测试通过。

## 3. 核心闭环

```text
创建任务
  → 固定仓库 commit
  → 建立测试失败基线
  → 分析 Issue/错误日志
  → 搜索并读取相关代码
  → 生成结构化补丁
  → 校验修改范围
  → 在隔离工作区应用补丁
  → 执行原测试与回归测试
  → 成功、继续修复、人工审核或回滚
```

### 3.1 LangGraph 状态

建议使用以下状态，而不是简单的同步函数串联：

`CREATED → BASELINE → LOCALIZE → PROPOSE_PATCH → APPLY_PATCH → VERIFY → FINISHED`

异常状态：

- `INVALID_TASK`：仓库、测试命令或任务参数不合法；
- `PATCH_REJECTED`：补丁格式错误、修改范围超限或修改测试文件；
- `VERIFY_FAILED`：测试仍失败或引入回归；
- `BUDGET_EXCEEDED`：超过修复次数、执行时间或资源预算；
- `NEEDS_REVIEW`：无法自动判断，转人工审核。

### 3.2 Agent 工具

第一版只提供必要工具：

- `list_files`：列出仓库文件；
- `search_code`：按关键词搜索代码；
- `read_file`：读取限定范围的文件；
- `apply_patch`：应用 unified diff；
- `run_tests`：执行允许的测试命令；
- `git_diff`：查看修改内容；
- `reset_workspace`：恢复到补丁前快照。

每个工具都需要记录输入、输出、耗时、错误和请求 ID，形成可复盘 trajectory。

## 4. 技术栈与掌握目标

| 技术 | 项目中的使用位置 | 需要真正掌握的内容 |
|---|---|---|
| Python | Agent 服务、适配器和评测 | 类型标注、异常分层、模块化、异步任务 |
| LangGraph | Agent 状态和条件分支 | State、节点、边、循环、checkpoint |
| FastAPI | 任务创建、状态查询和报告接口 | Pydantic、依赖注入、后台任务、错误响应 |
| GitPython / subprocess | 仓库快照、diff 和回滚 | commit、worktree、diff、命令返回码 |
| pytest | 测试基线、回归验证和评测 | fixture、参数化、测试收集、报告解析 |
| Docker | 隔离执行环境 | volume、网络、资源限制、临时容器 |
| tree-sitter 或 AST | 代码结构和修改范围分析 | 函数定位、语法解析、文件级门禁 |
| SQLite/PostgreSQL | 任务、轨迹和评测结果存储 | 表设计、索引、事务和查询 |
| Redis | 任务锁、缓存和过期状态 | key 设计、TTL、幂等和并发控制 |
| pytest + GitHub Actions | 自动回归和 CI | 单测、集成测试、质量门禁 |

技术栈不是为了凑关键词。每项技术都必须在代码、测试或运行记录中有明确使用证据。

## 5. 项目阶段规划

### 阶段一：理解 mini-SWE-agent

- 在本地或 Codespaces 跑通一个简单任务；
- 观察模型如何调用搜索、读取、编辑和测试工具；
- 阅读工具定义、任务循环和 trajectory 格式；
- 画出“模型—工具—工作区—测试”的关系图。

**阶段产物：** 一份运行记录、一次完整 trajectory 和架构笔记。

### 阶段二：实现本地单任务闭环

- 输入本地 Python 仓库和 Bug 描述；
- 完成文件搜索、文件读取、补丁应用和 pytest 执行；
- 先使用简单 Agent 循环，再迁移到 LangGraph；
- 保存每轮消息、工具调用和测试输出。

**阶段产物：** 能修复 3—5 个自建简单 Bug，并输出 diff 和测试报告。

### 阶段三：加入质量门禁

- 固定仓库 commit 和测试失败基线；
- 限制可修改文件和允许执行的命令；
- 检查补丁是否修改测试文件或越权访问路径；
- 实现最大修复轮数、超时、失败回滚和人工审核状态；
- 区分“测试通过”和“补丁可信”。

**阶段产物：** 至少一个被拦截的危险/越权案例和一个回滚案例。

### 阶段四：服务化与任务管理

- 使用 FastAPI 提供任务创建、状态查询和报告下载接口；
- 使用 SQLite/PostgreSQL 保存任务、轨迹、补丁和测试结果；
- 使用 Redis 实现任务锁、重复任务幂等和状态 TTL；
- 使用 Docker Compose 启动 API、数据库和执行器。

**阶段产物：** 从 API 创建任务到查询最终报告的完整流程。

### 阶段五：评测与扩展

- 构建 20—40 个小型 Python Bug 任务；
- 分类记录定位成功、补丁可应用、最终修复、回归引入和安全拦截；
- 使用 pytest 和 GitHub Actions 自动运行回归；
- 再考虑 Java/Maven 或 JavaScript/Jest 适配器；
- 根据真实失败样本增加代码结构检索、上下文压缩或模型对比。

**阶段产物：** 可复现评测报告和失败案例复盘。

## 6. 评测指标

| 指标 | 定义 |
|---|---|
| 定位成功率 | 是否找到与失败相关的代码位置 |
| 补丁应用率 | 生成 diff 能否安全应用 |
| 最终修复率 | 原失败测试和回归测试均通过的任务比例 |
| 回归引入率 | 修复后新增失败测试的任务比例 |
| 越权拦截率 | 修改受限文件或执行受限命令被拦截的比例 |
| 平均修复轮数 | 每个任务的 Agent 尝试次数 |
| 平均耗时/Token | 单任务资源成本 |

评测报告需要同时展示成功和失败任务，不使用没有测试集来源和判定规则的漂亮数字。

## 7. 最终简历叙事

### 7.1 项目标题

`PatchPilot - 面向软件仓库的测试失败诊断与补丁验证平台`

### 7.2 技术栈

`Python / LangGraph / FastAPI / pytest / Docker / Git / SQLite / Redis`

### 7.3 项目描述

> 面向受控软件仓库构建测试失败诊断与补丁验证 Agent，参考 SWE-agent 的工具循环设计，编排代码定位、补丁生成、隔离执行和回归验证流程，并通过 Git diff、测试基线和质量门禁判断修复结果。

### 7.4 简历 bullet 草案

- 基于 LangGraph 编排测试基线、失败分析、代码检索、补丁应用和回归验证节点，使用状态字段记录修复轮数、失败签名、变更文件和测试结果。
- 封装仓库搜索、文件读取、unified diff、测试执行和工作区回滚工具，记录每轮工具调用、耗时和错误，支持完整轨迹复盘。
- 使用 Docker 临时工作区、命令白名单、文件路径校验和资源限制执行测试；拦截测试文件修改、越权路径和超预算任务。
- 设计“原失败测试通过 + 相关回归测试通过 + 修改范围合法”的修复判定规则，避免仅依据单次测试返回码确认成功。
- 构建包含异常处理、边界条件、类型错误和数据访问错误的离线 Bug 集，评估定位成功率、补丁应用率、最终修复率和回归引入率。

所有数字必须在项目完成后根据真实运行记录填写。

## 8. 学习建议

### 8.1 学习顺序

1. 先掌握 Git：commit、branch、diff、worktree、stash 和回滚；
2. 再掌握 pytest：测试收集、fixture、参数化和失败输出；
3. 用 subprocess 独立实现安全的测试执行器；
4. 阅读 mini-SWE-agent，理解工具循环和 trajectory；
5. 学习 LangGraph 的 StateGraph、条件边、循环和 checkpoint；
6. 用 FastAPI 将单任务闭环服务化；
7. 学习 Docker 工作区和资源限制；
8. 最后增加 Redis、数据库、CI 和多语言适配。

### 8.2 每个阶段的学习方法

- 先手写一个最小版本，再让 AI 补齐重复代码；
- 每引入一个框架，先写出不用框架时的等价流程；
- 每个 Agent 节点都保留输入、输出和失败样例；
- 每周至少复盘一个失败任务，说明失败发生在哪个状态；
- 用流程图解释系统，不依赖“框架会自动处理”作为回答；
- 对外部项目只借鉴设计和接口，不复制大段代码。

### 8.3 你必须能独立解释的问题

- SWE-agent 的工具循环和普通聊天调用有什么区别？
- 为什么要固定 commit 和建立测试基线？
- 为什么测试通过不能直接代表补丁正确？
- 为什么补丁需要在临时工作区执行？
- Docker 隔离了什么，仍然有哪些风险？
- LangGraph 在这个项目中管理了哪些状态和分支？
- Agent 连续修复失败时如何终止和转人工？
- 如何防止 Agent 修改测试来伪造通过？
- 如何判断两个不同 Patch 都解决了同一个问题？
- 如何设计跨语言适配器而不把核心逻辑写死？

### 8.4 Vibe-coding 的使用边界

适合交给 AI：

- FastAPI CRUD、Pydantic 模型和基础 Repository；
- Docker Compose、CI 配置和样板代码；
- 测试数据生成、日志格式化和报告导出；
- 不同模型 SDK 的适配层。

必须自己掌握：

- 任务状态和状态转移；
- 工具协议和命令执行边界；
- Git 快照、diff、补丁应用和回滚；
- 测试通过的判定规则；
- Docker 隔离的能力边界；
- 评测指标和失败案例解释。

## 9. 风险控制与项目边界

- 首版只实现 Python/pytest 适配器，平台接口预留其他语言，不同时实现多种语言；
- 首版使用本地自建 Bug 集，不直接承诺 SWE-bench 成绩；
- 不把项目描述成 Codex、OpenHands 或 SWE-agent 的替代品；
- 不执行用户未授权的危险命令，不连接真实生产仓库；
- 如果 Agent 只能生成补丁但无法验证结果，项目不进入简历最终版本；
- 如果没有完整轨迹、失败案例和评测报告，项目只作为学习项目保留。

## 10. 项目完成标准

满足以下条件后，才建议把项目放进简历：

- 能从 API 或命令行创建一个完整任务；
- 至少修复一组自建 Bug，并保留成功与失败轨迹；
- 至少有一个补丁被安全门禁拦截；
- 至少有一个任务发生回滚或转人工；
- 有自动化测试和可复现评测报告；
- 能清楚解释 SWE-agent 的设计、自己的改动和未实现部分。
